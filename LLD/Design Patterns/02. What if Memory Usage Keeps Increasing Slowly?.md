# What if Memory Usage Keeps Increasing Slowly?
## Memory Leaks, Object Lifecycle, Flyweight, Weak References, Caching & GC Awareness 

---

### 🎯 Introduction: Jab "Silent Memory Leak" Production Ko Dheere-Dheere Kha Jaye

Backend interviews, production monitoring dashboards, aur incident post-mortems ka ek classic horror story hai: **"Memory usage graph slowly but steadily upar ja raha hai, koi spike nahi, koi error nahi… phir achanak OOMKill."**

Socho aapka microservice 2GB heap ke saath chal raha hai. Startup pe 800MB use ho raha hai. 6 hours baad 1.2GB. 24 hours baad 1.8GB. Koi memory spike nahi, koi obvious leak nahi dikh raha. Phir achanak: `java.lang.OutOfMemoryError: Java heap space`. Pod restart hota hai. Cycle repeat hota hai.

Yeh sirf "bad code" ka issue nahi hai. Yeh **object lifecycle mismanagement, caching without eviction, hidden references, aur GC tuning gaps** ka combined architectural challenge hai. Modern JVMs aur GC algorithms (G1, ZGC, Shenandoah) bohot advanced hain, lekin agar application layer pe references properly release nahi ho rahe, toh GC bhi helpless hai.

Is article mein hum isko zero-to-hero level pe cover karenge:
- Memory leak ke types: JVM level, application level, native memory
- Flyweight Pattern: Shared immutable state se memory optimize karna
- Weak/Soft/Phantom References: GC-friendly caching aur listener patterns
- Caching Strategies: TTL, LRU, size-based, adaptive eviction
- GC Awareness: Generational hypothesis, GC logs, tuning basics
- Real-world debugging: Heap dumps, MAT, async-profiler, JFR
- Interview traps, anti-patterns, production checklist

Chalo, step-by-step dive karte hain. 🔍

## 🔍 1. Memory Leak Ke Types: JVM vs Application vs Native

Java mein "memory leak" technically possible nahi hona chahiye (GC hai na!), lekin practical production mein yeh bohot common hai. Kyun? Kyunki **GC sirf unreachable objects ko collect karta hai**. Agar koi object reachable hai (even unintentionally), toh GC usse collect nahi karega.

### 📊 Memory Leak Categories:
| Type | Mechanism | Example |
|------|-----------|---------|
| **Static Collection Leak** | `static List/Map` mein objects add hote rehte hain, kabhi remove nahi hote | `static Map<String, UserSession> cache` without TTL/eviction |
| **Unclosed Resources** | `InputStream`, `Connection`, `ResultSet` close nahi hote → native memory leak | JDBC connection pool exhaustion, file descriptor leak |
| **Listener/Callback Leak** | Event listener register hota hai, unregister nahi hota → publisher holds reference | `ApplicationListener`, `Observer`, `CompletableFuture` callbacks |
| **ThreadLocal Leak** | `ThreadLocal` values cleared nahi hote, thread pool reuse ke saath accumulate | Web app context, MDC, user context in thread pools |
| **Inner Class Reference** | Non-static inner class holds implicit reference to outer class instance | Anonymous `Runnable` inside long-lived object |
| **ClassLoader Leak** | Old classloader + all its classes retained due to static/ThreadLocal refs | Hot deploy, OSGi, application server redeploy |
| **Native Memory Leak** | Direct `ByteBuffer`, JNI calls, off-heap libraries leak native memory | Netty direct buffers, RocksDB, TensorFlow JNI |

### 📉 Slow Growth vs Sudden Spike:
```
Slow Growth (Leak):     ████████████████████→ (linear/exponential creep)
Sudden Spike (Burst):   ████████▁▁▁▁▁▁▁▁▁▁▁▁→ (then GC recovers)
OOM Pattern:            ████████████████████▓▓→ [OOMKill]
```

👉 **Rule:** Agar heap usage **monotonically increasing** hai aur Full GC ke baad bhi reclaim nahi ho raha → leak confirm hai. Spike + recovery = normal GC behavior.

## 🪶 2. Flyweight Pattern: Shared Immutable State se Memory Bachana

Flyweight pattern ka funda simple hai: **"Agar bohot saare objects same data share kar rahe hain, toh ek common instance banao aur references share karo."**

### 🔧 Classic Example: Text Editor Characters
```java
// ❌ Without Flyweight: Har character ka alag object
class Character {
    char symbol;
    String font;
    int size;
    String color;
    // 10,000 characters = 10,000 objects × 4 fields each
}

// ✅ With Flyweight: Intrinsic (shared) + Extrinsic (unique) state
class CharacterFlyweight {
    // Intrinsic: Shared, immutable
    private final String font;
    private final int size;
    private final String color;
    
    // Extrinsic: Passed at runtime
    public void render(char symbol, int x, int y) {
        // render logic using shared style + unique position/symbol
    }
}

// Flyweight Factory with caching
class CharacterFactory {
    private static final Map<String, CharacterFlyweight> cache = new ConcurrentHashMap<>();
    
    public static CharacterFlyweight get(String font, int size, String color) {
        String key = font + ":" + size + ":" + color;
        return cache.computeIfAbsent(key, k -> 
            new CharacterFlyweight(font, size, color)
        );
    }
}
```

### 💻 Modern Java Use Cases:

#### 1. String Interning (Built-in Flyweight)
```java
String a = new String("hello");
String b = new String("hello");
System.out.println(a == b); // false

String c = a.intern();
String d = b.intern();
System.out.println(c == d); // true → same pool reference
```
**Caution:** `intern()` string pool mein permanent reference daalta hai. Unbounded user input ko intern mat karo → PermGen/Metaspace OOM.

#### 2. Enum as Flyweight
```java
public enum HttpStatus {
    OK(200, "OK"), NOT_FOUND(404, "Not Found"), ...;
    
    private final int code;
    private final String message;
    
    HttpStatus(int code, String message) {
        this.code = code;
        this.message = message;
    }
    // All usages share same enum instance → zero allocation overhead
}
```

#### 3. Immutable Value Objects with Factory Cache
```java
public final class Money {
    private final BigDecimal amount;
    private final Currency currency;
    
    private static final Map<String, Money> cache = new ConcurrentHashMap<>();
    
    private Money(BigDecimal amount, Currency currency) {
        this.amount = amount;
        this.currency = currency;
    }
    
    public static Money of(BigDecimal amount, Currency currency) {
        String key = amount + ":" + currency.getCurrencyCode();
        return cache.computeIfAbsent(key, k -> new Money(amount, currency));
    }
}
```

### ⚖️ Flyweight Trade-offs:
| Benefit | Cost |
|---------|------|
| Massive memory reduction for repeated values | Factory/cache complexity, thread-safety overhead |
| Faster equality checks (reference ==) | Immutability requirement, no per-instance mutation |
| Better CPU cache locality (shared data) | Cache eviction logic needed for unbounded keys |

👉 **Rule:** Flyweight tabhi use karo jab:
1. Objects are **immutable** or effectively immutable
2. **High duplication** of intrinsic state (>1000 instances with same values)
3. Identity comparison (`==`) is acceptable or desired

## 🕸️ 3. Weak/Soft/Phantom References: GC-Friendly Object Holding

Java ki `Reference` classes (`WeakReference`, `SoftReference`, `PhantomReference`) allow karti hain ki aap object ko "hold" karo lekin GC ko permission do ki agar memory pressure aaye toh collect kar le.

### 🔗 Reference Types Comparison:
| Type | GC Behavior | Use Case | Example |
|------|-------------|----------|---------|
| **Strong** (default) | Never collected while reachable | Normal objects | `Object obj = new Object();` |
| **SoftReference** | Collected only when JVM is low on memory | Memory-sensitive caches | Image cache, large result sets |
| **WeakReference** | Collected in next GC cycle if no strong refs | Canonical mappings, listeners | `WeakHashMap`, event listeners |
| **PhantomReference** | Enqueued after finalization, for cleanup | Resource deallocation, native memory | DirectByteBuffer cleanup |

### 💻 Practical Implementations:

#### 1. `WeakHashMap` for Canonical Mappings
```java
// Use case: Class metadata cache that auto-cleans when ClassLoader is GC'd
private static final WeakHashMap<Class<?>, Metadata> metadataCache = new WeakHashMap<>();

public Metadata getMetadata(Class<?> clazz) {
    return metadataCache.computeIfAbsent(clazz, this::computeMetadata);
    // When clazz is no longer strongly reachable, entry auto-removed
}
```

#### 2. `SoftReference` for LRU-like Cache
```java
public class SoftCache<K, V> {
    private final Map<K, SoftReference<V>> cache = new ConcurrentHashMap<>();
    private final ReferenceQueue<V> queue = new ReferenceQueue<>();
    
    public void put(K key, V value) {
        cleanup(); // Remove collected references
        cache.put(key, new SoftReference<>(value, queue));
    }
    
    public V get(K key) {
        cleanup();
        SoftReference<V> ref = cache.get(key);
        return ref == null ? null : ref.get(); // null if collected
    }
    
    private void cleanup() {
        Reference<? extends V> ref;
        while ((ref = queue.poll()) != null) {
            // Remove from map if this reference was collected
            cache.values().removeIf(r -> r == ref);
        }
    }
}
```

#### 3. `PhantomReference` for Native Resource Cleanup
```java
// Advanced: When DirectByteBuffer is collected, clean native memory
public class NativeResource {
    private long nativeHandle;
    
    public NativeResource(long handle) {
        this.nativeHandle = handle;
        PhantomReference<NativeResource> ref = 
            new PhantomReference<>(this, cleanupQueue) {
                @Override
                public void clear() {
                    super.clear();
                    if (nativeHandle != 0) {
                        nativeFree(nativeHandle); // JNI call
                        nativeHandle = 0;
                    }
                }
            };
    }
}
```

### ⚠️ Critical Gotchas:
```java
// ❌ WeakReference ka value directly use mat karo bina null check
WeakReference<User> ref = new WeakReference<>(user);
User u = ref.get(); // Can be null anytime!
if (u != null) { /* use u */ }

// ❌ SoftReference cache mein eviction policy bhi add karo
// Sirf SoftReference rely mat karo → GC timing unpredictable hota hai
```

👉 **Rule:** Weak/Soft references **optimization tools** hain, correctness guarantees nahi. Hamesha null-check karo, aur fallback logic rakho.

## 🗃️ 4. Caching Strategies: TTL, LRU, Size-Based, Adaptive

Caching memory leak ka sabse common cause hai: **"Cache add karte raho, kabhi remove mat karo."**

### 📊 Cache Eviction Strategies:
| Strategy | How It Works | Best For | Java Implementation |
|----------|--------------|----------|-------------------|
| **TTL (Time-To-Live)** | Entry expires after fixed duration | Session data, API responses | Caffeine `expireAfterWrite`, Redis `EXPIRE` |
| **TTI (Time-To-Idle)** | Entry expires after last access | User-specific data, hot items | Caffeine `expireAfterAccess` |
| **LRU (Least Recently Used)** | Evict least recently accessed when full | General purpose cache | `LinkedHashMap` with `removeEldestEntry`, Caffeine |
| **LFU (Least Frequently Used)** | Evict least frequently accessed | Read-heavy, skewed access patterns | Caffeine `weigher` + custom policy |
| **Size-Based** | Evict when cache size/weight exceeds limit | Memory-constrained environments | Caffeine `maximumSize`, `maximumWeight` |
| **Adaptive** | Dynamically adjust policy based on hit rate | Production systems with varying load | Caffeine `recordStats()`, custom policies |

### 💻 Caffeine Cache (Modern Standard):
```java
LoadingCache<String, User> cache = Caffeine.newBuilder()
    .maximumSize(10_000)           // Size-based eviction
    .expireAfterWrite(10, TimeUnit.MINUTES)  // TTL
    .expireAfterAccess(5, TimeUnit.MINUTES)  // TTI
    .recordStats()                 // Enable metrics
    .removalListener((key, value, cause) -> {
        if (cause == RemovalCause.SIZE) {
            log.debug("Evicted due to size: {}", key);
        }
    })
    .build(key -> loadUserFromDb(key)); // Loader function

// Usage
User user = cache.get("user:1001"); // Sync load if missing
AsyncLoadingCache<String, User> asyncCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .buildAsync(key -> loadUserAsync(key)); // Async load
```

### 📈 Cache Monitoring Metrics:
```yaml
cache.metrics:
  hit_rate: caffeine.cache.hitRate  # Target: >80%
  miss_rate: caffeine.cache.missRate
  eviction_count: caffeine.cache.eviction.count
  eviction_weight: caffeine.cache.eviction.weight
  load_success: caffeine.cache.load.success.count
  load_failure: caffeine.cache.load.failure.count
  population: caffeine.cache.size
```

### ⚖️ Cache Trade-offs:
| Strategy | Pros | Cons |
|----------|------|------|
| **TTL** | Simple, predictable memory bound | May evict hot data prematurely |
| **LRU** | Keeps frequently accessed data | Requires tracking access order (overhead) |
| **LFU** | Optimal for skewed access patterns | Complex, needs frequency tracking |
| **Adaptive** | Self-tuning, production-ready | Black-box behavior, harder to debug |

👉 **Rule:** Cache hamesha **bounded + evictable** hona chahiye. Unbounded cache = guaranteed memory leak over time.

## ♻️ 5. Garbage Collection Awareness: Generational Hypothesis & Tuning Basics

GC ko "magic" mat samjho. Uske behavior ko samajhkar aap application ko GC-friendly design kar sakte ho.

### 🧬 Generational Hypothesis (JVM Core Principle):
```
Heap Memory Layout:
┌─────────────────────────┐
│   Young Generation      │
│  ┌─────┬─────┬─────┐   │
│  │Eden │ S0  │ S1  │   │ ← Most objects die here (90%+)
│  └─────┴─────┴─────┘   │
├─────────────────────────┤
│   Old Generation        │ ← Long-lived objects promoted here
│  (Tenured)              │
├─────────────────────────┤
│   Metaspace (Java 8+)   │ ← Class metadata, not GC'd often
└─────────────────────────┘
```

### 🔁 GC Cycle Types:
| GC Type | Scope | Pause Time | Frequency | Use Case |
|---------|-------|------------|-----------|----------|
| **Minor GC** | Young Gen only | Short (ms) | Frequent | Normal allocation |
| **Major GC** | Old Gen | Medium (10-100ms) | Occasional | Long-lived objects |
| **Full GC** | Entire heap + metaspace | Long (100ms-seconds) | Rare | Memory pressure, System.gc() |

### 🛠️ GC Algorithms Comparison (Java 8-21):
| Algorithm | Pause Goal | Throughput | Best For | JVM Flag |
|-----------|------------|------------|----------|----------|
| **Parallel GC** | Throughput | High | Batch processing | `-XX:+UseParallelGC` |
| **CMS** (Deprecated) | Low pause | Medium | Low-latency apps | `-XX:+UseConcMarkSweepGC` |
| **G1GC** (Default Java 9+) | Predictable pause | High-Medium | General purpose | `-XX:+UseG1GC` |
| **ZGC** (Java 11+, prod-ready Java 15+) | <10ms pause | Medium-High | Ultra-low latency | `-XX:+UseZGC` |
| **Shenandoah** (Java 12+) | <10ms pause | Medium | Large heaps (>32GB) | `-XX:+UseShenandoahGC` |

### 🔍 GC Logging & Analysis:
```bash
# Enable GC logs (Java 9+)
-XX:+UseG1GC -Xlog:gc*:file=gc.log:time,uptime,level,tags

# Analyze with GCViewer or gceasy.io
# Key metrics to watch:
# - Pause time (target: <100ms for G1, <10ms for ZGC)
# - GC frequency (too frequent = memory pressure)
# - Heap occupancy after GC (should drop significantly)

# JFR for production-safe profiling
jcmd <pid> JFR.start name=gcprof duration=60s settings=profile
jcmd <pid> JFR.dump name=gcprof filename=gc.jfr
```

### 📊 GC-Friendly Coding Practices:
```java
// ✅ Prefer short-lived objects (Young Gen optimized for this)
public void process(Request req) {
    Response resp = buildResponse(req); // Dies after method
    send(resp);
}

// ❌ Avoid promoting short-lived objects to Old Gen
private static List<Temporary> cache = new ArrayList<>(); // Static = Old Gen candidate

// ✅ Reuse buffers where possible (but don't leak them)
private static final ThreadLocal<byte[]> buffer = 
    ThreadLocal.withInitial(() -> new byte[8192]);

// ❌ Don't hold large arrays in long-lived objects
public class LeakyService {
    private byte[] hugeBuffer = new byte[100_000_000]; // 100MB stuck in Old Gen
}
```

👉 **Rule:** GC tuning **last step** hai. Pehle application-level leaks fix karo, cache bound karo, references manage karo. Phir GC algorithm tune karo.

## 🕵️‍♂️ 6. Debugging Memory Leaks: Heap Dumps, MAT, Profilers

Jab memory slowly badhne lage, toh blind guess mat karo. Scientific approach use karo.

### 🔧 Step-by-Step Debugging Workflow:

#### Step 1: Confirm It's a Leak
```bash
# Monitor heap over time
jstat -gcutil <pid> 5000  # Every 5 seconds

# Look for: Old Gen occupancy increasing, Full GC not reclaiming much
# Example output:
# S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
# 0.00  12.34  45.67  78.90  90.12  85.34   150    12.34    5     2.10    14.44
# 0.00  11.23  44.56  82.10  90.15  85.40   160    13.45    6     2.50    15.95  ← Old Gen creeping up
```

#### Step 2: Take Heap Dump
```bash
# On OOM (automatic)
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/heap.hprof

# Manual dump (production-safe if heap < 4GB)
jmap -dump:live,format=b,file=heap.hprof <pid>

# For large heaps, use jcmd (less intrusive)
jcmd <pid> GC.heap_dump /var/log/heap.hprof
```

#### Step 3: Analyze with Eclipse MAT (Memory Analyzer Tool)
```
1. Open heap.hprof in MAT
2. Run "Leak Suspects Report" (automatic)
3. Check "Dominator Tree" → largest retained heap
4. Check "Path to GC Roots" → why is this object not collected?
5. Look for: static collections, ThreadLocal maps, unclosed resources
```

#### Step 4: Profile Allocation with Async-Profiler
```bash
# Record allocations for 60 seconds
./profiler.sh -e alloc -d 60 -f alloc.html <pid>

# Open alloc.html in browser
# Look for: Which classes/methods allocate most memory?
# Correlate with business logic: Is this expected or leak?
```

#### Step 5: JFR for Production-Safe Deep Dive
```bash
# Start recording
jcmd <pid> JFR.start name=memprof duration=300s settings=profile

# Stop and dump
jcmd <pid> JFR.stop name=memprof
jcmd <pid> JFR.dump name=memprof filename=memprof.jfr

# Analyze in JDK Mission Control or online tools
```

### 🎯 Common Leak Patterns in MAT:
| Pattern | What to Look For | Fix |
|---------|-----------------|-----|
| **Static Collection** | `static Map/List` with large retained heap | Add TTL, use WeakHashMap, or bounded cache |
| **ThreadLocal Leak** | `ThreadLocal$ThreadLocalMap$Entry[]` growing | Remove in `finally`, use try-with-resources pattern |
| **Listener Leak** | Many instances of same listener class | Unregister in cleanup, use WeakReference for listeners |
| **ClassLoader Leak** | Multiple `WebappClassLoader` instances | Check static refs, ThreadLocals, JDBC driver deregister |
| **Native Memory** | Heap dump small but process RSS large | Check DirectByteBuffers, JNI, off-heap libraries |

## 🌐 7. Real-World Scenarios & Architecture Patterns

### 🛒 Scenario 1: E-Commerce Session Cache
**Problem:** User sessions stored in `static Map`, never evicted → heap grows 1GB/day.

**Solution:**
- Replace with Caffeine cache: `maximumSize(100_000)`, `expireAfterAccess(30, MINUTES)`
- Use `WeakReference` for non-critical session metadata
- Monitor `cache.eviction.count` and alert on high eviction rate
- GC: G1GC with `-XX:MaxGCPauseMillis=200`

### 🏦 Scenario 2: Banking Transaction Logger
**Problem:** `List<Transaction> auditLog` in service class → OOM after 1M transactions.

**Solution:**
- Async logging to Kafka/DB, not in-memory list
- If caching needed: bounded ring buffer (`ArrayBlockingQueue` with drop-oldest)
- Use `SoftReference` for recent transactions (auto-evict under memory pressure)
- Add `@PreDestroy` hook to flush remaining logs on shutdown

### 🎮 Scenario 3: Game Server Entity Manager
**Problem:** 10k game entities, each with 50KB state → 500MB just for entities. Frequent create/destroy.

**Solution:**
- Flyweight pattern for shared assets (textures, sounds, config)
- Object pool for entity components (reusable buffers)
- `WeakHashMap<EntityId, Entity>` for auto-cleanup when entity dereferenced
- ZGC for sub-10ms pause times during gameplay

## ⚠️ 9. Anti-Patterns & Production Gotchas

| Anti-Pattern | Why It's Bad | Fix |
|--------------|--------------|-----|
| `static Map/List` without bounds | Unbounded growth → guaranteed OOM over time | Use bounded cache (Caffeine), WeakHashMap, or DB-backed storage |
| ThreadLocal without `remove()` in finally | Thread pool reuse → values accumulate across requests | Always `threadLocal.remove()` in `finally` block, or use try-with-resources pattern |
| Caching without eviction policy | "It's just a cache" → becomes memory leak | TTL, LRU, size-based eviction mandatory. Monitor eviction metrics. |
| Ignoring native memory (DirectByteBuffer) | Heap dump small but process killed by OOMKill | Monitor `sun.nio.ch.directBuffer.capacity`, use `Cleaner` or PhantomReference |
| Calling `System.gc()` in code | Unpredictable pauses, JVM ignores it anyway | Let JVM manage GC. Tune GC flags if needed, don't force GC in code. |
| Large objects in long-lived scope | Promoted to Old Gen → Full GC pressure | Keep large allocations short-lived, reuse buffers via pooling |

## 🧰 10. Production-Ready Checklist

✅ All caches are bounded + have eviction policy (TTL/LRU/size)  
✅ ThreadLocal values removed in `finally` blocks or use scoped cleanup  
✅ Weak/Soft references used appropriately with null-check fallbacks  
✅ Heap dump enabled on OOM: `-XX:+HeapDumpOnOutOfMemoryError`  
✅ GC logging enabled for analysis: `-Xlog:gc*:file=gc.log:time,uptime`  
✅ APM metrics for memory: heap usage, GC pause time, cache hit/eviction rates  
✅ Alerting configured: Old Gen > 80%, Full GC frequency > threshold  
✅ Load testing includes long-running scenarios (24h+) to catch slow leaks  
✅ Documentation: Cache configs, GC flags, leak debugging procedures recorded  
✅ Regular heap dump analysis in staging to catch leaks before production

## 📝 Summary & Key Takeaways

Slow memory growth ek **silent killer** hai. Yeh crash tab karta hai jab system peak load pe hota hai. Isko handle karne ke liye:

1. **Leak Types Samjho:** Static collections, ThreadLocals, listeners, native memory – har type ka detection aur fix alag hai.
2. **Flyweight for Duplication:** Agar bohot saare objects same data share kar rahe hain, toh shared immutable instance use karo.
3. **Weak/Soft References = Optimization, Not Correctness:** GC-friendly holding ke liye useful, lekin hamesha null-check aur fallback rakho.
4. **Cache Bounded + Evictable:** Unbounded cache = guaranteed leak. Caffeine/Guava use karo with explicit eviction policies.
5. **GC Awareness, Not GC Dependency:** GC ko magic mat samjho. Application-level fixes pehle, GC tuning baad mein.
6. **Debug Scientifically:** Heap dumps, MAT, async-profiler, JFR – in tools ke bina aap guess kar rahe ho.

Backend interviews aur production readiness mein interviewer/ops team dekhna chahta hai ki aap:
- Memory management ko JVM architecture ke context mein samajhte hain
- Patterns (Flyweight, Weak refs, caching) ke exact boundaries jaante hain
- Production debugging workflow (heap dump → MAT → fix) practically jaante hain
- "Prevent, monitor, recover" mindset rakhte hain
