## 1. Redis Crash Hone Ka Asli Matlab Kya Hai?

Redis ek in-memory data store hai jo microsecond latency ke saath cache, session store, rate limiter, ya message queue ki tarah kaam karta hai. Aapne apni poori application ki performance iske bharose laga rakhi hai. Lekin ek din, achaanak Redis process crash ho jaata hai — OOM kill, segfault, ya server reboot. Usi pal aapki application ke paas cache nahi raha. Har request jo pehle cache se turant response le rahi thi, ab directly database pe jaane lagti hai. Database pe 10x, 20x load badh jaata hai. Connection pool exhaust, queries queue, CPU 100%, poori application slow, timeout, aur kabhi-kabhi poora collapse. Is collapse ki speed bahut tez hoti hai, aur ise hum **Cache Stampede** kehte hain — jaise bina umbrella ke barish mein bheegna.

Redis crash hone ka matlab sirf "cache missing" nahi hai; ye ek reliability event hai jo aapke infrastructure ki asli elasticity ko test karta hai. Agar aapne Redis ko high availability ke saath design nahi kiya, to ye ek choti si outage puri production raat ko din mein badal sakti hai.

**Is Scenario Mein Shamil Topics:**
- **Cache Stampede:** Jab cache miss ki vajah se saare requests ek saath database pe jaate hain, use overload karte hain.
- **High Availability (HA):** Redis ko is tarah setup karna ki ek node fail ho to doosra turant le le, bina application impact ke.
- **Replication:** Primary (master) se data automatically copy hota hai doosre nodes (replicas) pe.
- **Redis Sentinel:** Redis ke official HA solution jo monitoring, notification, aur automatic failover provide karta hai.
- **Redis Cluster:** Data ko multiple shards mein partition karta hai, har shard ke replicas hote hain, built-in failover.
- **Failover Handling:** Jab master fail hota hai, to replica ko promote karna, clients ko new master ke bare mein batana.
- **Cache Warming:** Crash ke baad jab Redis wapas aata hai, to cache empty hota hai. Usse dheere-dheere data populate karna taaki database stampede na ho.

## 2. Real-World Example: E-Commerce Flash Sale Mein Redis Crash

Maan lo ek e-commerce platform hai jahaan product listing aur price data Redis mein cache hota hai. Redis setup: ek single master node (no replication, no sentinel). Application: Java Spring Boot, Redis connection pool (Lettuce).

**Incident Sequence:**
- Flash sale subah 10 baje shuru. Traffic spike. Redis ke paas lakhon keys, memory usage 90%. TTL expiry ke saath `maxmemory-policy` `noeviction` tha.
- Redis ke paas suddenly `FLUSHALL` command execute ho gaya — kisi developer ne test script production mein chala di (human error). Saari keys gayab. Redis alive tha, lekin cache empty.
- Har product page request ke liye application ne Redis check kiya — miss. Database (MySQL) se product fetch kiya. Cache set karne ke liye Redis call, but under high load Redis bhi slow tha.
- Database par normally 2,000 queries per second the, ab 20,000 pahunch gaye. DB CPU 100%, connection pool 2000 connections full, new queries queue. Application threads block, timeout.
- Poori site 5xx errors dena shuru. Users ko blank page. Sale failed, revenue loss, brand damage.

**Root Cause:** Single point of failure (SPOF) Redis, no high availability, no replication, no circuit breaker to protect DB, no cache warming strategy.

## 3. Redis Crash Kyun Hota Hai? (Root Cause Tree)

### 3.1 Memory Exhaustion (OOM)
- `maxmemory` limit set nahi, ya set hai lekin eviction policy `noeviction`, aur writes hoti rahi. Redis process system OOM killer se kill.
- Fragmented memory ya big key size se memory spike.

### 3.2 Human Error
- Galati se `FLUSHALL`, `FLUSHDB`, ya `KEYS *` chala diya production mein.
- Deployment script mein galat config, Redis restart.

### 3.3 Persistence Related Crashes
- RDB snapshot ya AOF rewrite ke dauran disk full ho gaya, Redis I/O error se exit.
- AOF file corrupt, Redis start nahi hota.

### 3.4 Software Bugs / Version Incompatibility
- Redis server version mein bug jisse crash.
- Client library bug: connection pool leak, Redis overload.

### 3.5 Infrastructure Failure
- Cloud VM (EC2) termination, power failure, network partition.
- Kubernetes pod eviction, disk pressure.

### 3.6 DDoS / Overload
- Too many client connections (maxclients limit hit).
- Slow commands (e.g., `SORT`, `KEYS`, `SMEMBERS` on large sets) block Redis single thread, health check fail, clients disconnect, crash.

## 4. Redis Crash Khatarnak Kyun Hai? (Impact & Cache Stampede)

### 4.1 Direct Database Overload (Cache Stampede)
- Saare requests database pe. DB capacity exceed, connection pool exhaust, queries slow, lock contention, crash. Application down.

### 4.2 Increased Latency & Timeouts
- Redis response time <1ms tha, DB response time 50ms ho gaya, aur load ke saath 5 sec. APIs timeout, client retry, aur load.

### 4.3 Session Data Loss (User Logout)
- Agar Redis session store ke liye use ho raha tha, to saare users logged out. Login service pe spike.

### 4.4 Rate Limiting Failure
- Agar Redis rate limiter ke liye use hota tha, to crash ke baad rate limiting fail, ya aggressive fail-safe block kare.

### 4.5 Lost Message Queue / Job State
- Redis-based queues (Bull, Celery) ke pending jobs lost. Critical async tasks fail.

### 4.6 Cascading Failures
- Multiple services same Redis cluster use karte hain. Ek service ka Redis crash poore microservice ecosystem ko affect karega.

### 4.7 Recovery Complications (Cache Warming)
- Redis wapas aata hai, but cache empty. Use turant populate karne ke liye DB pe fir se load. Agar cache warming strategy nahi, to fir se crash ho sakta hai DB.

## 5. Companies Redis Crash Ko Kaise Handle Karti Hain? (Solutions with Examples)

### 5.1 Redis Replication (Read Replicas for Read Scalability)
- Ek primary aur ek ya multiple replicas. Replicas read-only. Agar primary crash, to replica ko manually promote karo `SLAVEOF NO ONE`. Downtime thoda, but manual step se failover slow.
- **Example:** Basic Redis setup: primary (`redis-server --port 6379`), replica (`redis-server --port 6380 --slaveof 127.0.0.1 6379`). Reads ke liye application replicas use kare, writes primary pe. Crash pe manual intervention.

### 5.2 Redis Sentinel (Automatic Failover)
- Sentinel ek daemon hai jo Redis nodes ko monitor karta hai. Agar primary down, to Sentinel automatic failover karta hai: replica ko promote, clients ko naye master ka address bhejta hai via pub/sub ya configuration update.
- **Architecture:** Minimum 3 Sentinel nodes for quorum. Application client (Lettuce, Jedis) Sentinel-aware configuration: `RedisURI.Builder.sentinel("sentinel1", 26379, "mymaster").build()`.
- **Example:** AWS ElastiCache Redis with Multi-AZ (behind the scenes Sentinel use karta hai). Primary fail -> automatic failover within 1-2 minutes. Application reconnects.

### 5.3 Redis Cluster (Sharding + HA)
- Data multiple shards (master nodes) mein partitioned hota hai (16384 hash slots). Har shard ke replicas hain. Agar ek master crash, to cluster automatically uski replica ko promote karta hai. Failover < 1 minute.
- **Example:** Twitter-scale Redis Cluster with hundreds of nodes. Client (JedisCluster) automatically discovers topology, routes requests to correct master. Shard fail hone par replica master ban jaata hai, client transparently reconnects.

### 5.4 Application-Level Resilience: Circuit Breaker & Fallback
- Redis unavailable ho to turant DB pe mat bhejo. Circuit breaker (Resilience4j) use karo: agar Redis calls fail > 50%, circuit open, immediately return fallback (e.g., empty data, or use local cache).
- **Example:** Spring Cloud Circuit Breaker around Redis calls. Fallback: `return Optional.empty()` ya in-memory Caffeine cache se stale data serve karo.

### 5.5 Cache Stampede Prevention (Request Coalescing)
- Cache miss ke time ek hi key ke liye saare concurrent threads DB ko hit na karein. Sirf ek thread ko DB call karne do, baaki wait karein (singleflight pattern).
- **Example:** Spring `@Cacheable(sync = true)` ensures only one thread loads data, others wait for the cache entry. Or use `CompletableFuture` based lock per key.

### 5.6 Cache Warming (Cold Start Handling)
- Redis wapas aane par turant load na bhejo. Gradually cache populate karo using:
  - **Pre-loading scripts:** Database se common keys load karo (e.g., top 10k products).
  - **Lazy loading with throttling:** Cache miss pe async populate karo, but rate limit DB calls.
  - **Warm-up endpoints:** Load balancer health check ke through traffic tabhi bhejo jab cache warm ho.
- **Example:** Netflix uses "Cache Warming" before taking a region live: pre-computed data loaded into Redis, then traffic shifted.

### 5.7 Multi-Region Redis with Global Datastore
- AWS ElastiCache Global Datastore: cross-region replication. Agar poora region fail, doosre region ka Redis cluster data serve kare. Automatic failover with RPO near zero.
- **Example:** Active-active multi-region application, each region has local Redis, writes replicated globally.

### 5.8 Monitoring & Alerting for Redis Health
- Redis metrics: `redis_up`, `connected_clients`, `used_memory_rss`, `evicted_keys`, `replication_lag`, `sentinel_known_slaves`.
- Auto-healing: Kubernetes liveness probe restart Redis if unresponsive, StatefulSet with persistent volume AOF recovery.

## 6. Real Project Scenario: Food Delivery App Redis Crash Recovery

**Company:** Food delivery app. Redis used for: restaurant menu cache, user session store, driver location cache (geospatial). Setup: ElastiCache Redis Cluster with 3 shards, each shard 1 primary + 1 replica, Multi-AZ disabled (cost saving). No Sentinel (Cluster handles failover internally). Client: Lettuce with cluster topology refresh.

**Incident:** One primary node in shard 1 crashed due to underlying hardware failure. Redis Cluster started failover: replica promoted to primary. However, during failover (30 seconds), the cluster was partitioned: some nodes saw old primary, some new. Lettuce client topology refresh was set to 60 seconds, so it continued sending requests to old primary IP, getting connection errors. Application saw intermittent Redis timeouts for 1 minute.

**Impact:** During those 30-60 seconds, restaurant menu cache misses hit database. Database, which was already under moderate load, had a sudden spike. Menu queries became slow, overall API latency increased. Some driver location updates failed, affecting real-time tracking. User complaints about slow app.

**Root Cause:** Client topology refresh interval too long, no circuit breaker, no fallback for cache miss, no separate local cache.

**Fix Applied:**
1. **Client Topology Refresh Tuning:** Lettuce client configuration: `ClusterTopologyRefreshOptions.enabled()` with refresh period 5 seconds, also enable `closeStaleConnections` and `adaptiveRefreshTriggers`.
2. **Circuit Breaker on Redis:** Added Resilience4j circuit breaker for Redis calls. Fallback: for menu cache miss, return empty list (show "menu not available temporarily") instead of hitting DB; or use local Caffeine cache (TTL 1 min) as last-resort fallback.
3. **Read-Aside with DB Protection:** All cache miss DB calls wrapped with `@Cacheable(sync = true)` to prevent thundering herd. Also, DB connection pool increase to handle burst if needed.
4. **Redis Cluster Multi-AZ Enabled:** Enabled Multi-AZ for ElastiCache (automatic). So that if an AZ goes down, replicas in other AZ promoted.
5. **Cache Warming on Failover:** Created a script that detects master change event (via ElastiCache events) and pre-loads critical menu data from DB into the new primary.
6. **Driver Location Cache Fallback:** Used local in-memory map with TTL 10 seconds for driver locations; if Redis miss, use local map to avoid affecting tracking.
7. **Monitoring:** Dashboard showing Redis Cluster health (nodes up), client connection errors, circuit breaker state, fallback usage. Alert if any primary down for > 30 sec.

**Result:** Next failover happened due to AZ maintenance; cluster recovered in 10 seconds, application circuit breaker opened briefly, fallback served local cache, users experienced minimal lag, no DB overload.

## 7. Monitoring & Alerting for Redis Crash

| Metric | How to Track | Alert if |
|--------|--------------|----------|
| **redis_up** (node availability) | Redis exporter `redis_up` | 0 for any node > 10 sec |
| **connected_clients** | `redis_connected_clients` | Spike or sharp drop |
| **used_memory_rss vs maxmemory** | `redis_used_memory_rss` | > 90% of maxmemory |
| **evicted_keys** | `redis_evicted_keys_total` | Rate > 0 (if noeviction) or high rate (pressure) |
| **rejected_connections** | `redis_rejected_connections_total` | > 0 |
| **replication_lag** | `redis_repl_backlog_histlen` or slave `lag` | > 5 seconds |
| **sentinel_known_slaves (if sentinel)** | `redis_sentinel_slaves` | < expected slaves count |
| **cluster_state (if cluster)** | `redis_cluster_state` | not 1 (ok) |
| **cache hit ratio** | `keyspace_hits` / (`hits + misses`) | Sharp drop to 0 |
| **Circuit breaker state (application)** | Resilience4j metrics | Open |
| **Application fallback usage** | Custom counter | Spike |
| **DB load spike during Redis down** | DB connections, CPU | Sudden increase |

**Tools:** Prometheus + Grafana, Redis Exporter, ElastiCache CloudWatch metrics, PagerDuty.

## 8. Sabse Badi Seekh (Core Principle)

Redis crash hone par aapka database nahi bachna chahiye. Redis ek performance accelerator hai, lifeline nahi. Isliye high availability with automatic failover (Sentinel/Cluster) to table stakes hai. Lekin usse bhi important hai **application ki resilience**: circuit breakers, fallbacks, request coalescing, aur cache warming ke bina aap Redis ke bina survive nahi kar sakte. Redis ko ek reliable distributed component ki tarah treat karo, na ki ek in-memory magic box.

**Mantra:**
> "Redis gira to database bachega kaise? Sentinel failover, cluster sharding, aur application ke circuit breaker se. Cache stampede ko roko singleflight se, aur cold start mein cache warming se. Redis high availability ka asli matlab ye nahi ki Redis kabhi na gire; asli matlab hai ki jab gire to poora system na dhare. Ek mature distributed system Redis ke bina bhi muskurata hai, thoda slow sahi, lekin zinda."
