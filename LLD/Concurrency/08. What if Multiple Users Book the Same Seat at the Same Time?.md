# What if Multiple Users Book the Same Seat at the Same Time?
### 🎯 Introduction: Jab "Ek Seat" Ke Liye 100 Log Ek Saath Click Karte Hain

Backend interviews aur real-world production systems ka sabse iconic scenario: **Double Booking / Overbooking**. 

Socho ek concert ka ticket launch hua. 50,000 users ne 10,000 seats ke liye "Book Now" dabaya. Agar system properly designed nahi hai, toh:
- 15,000 bookings confirm ho jati hain
- Payment gateway successfully charge kar deta hai
- Baad mein system ko pata chalta hai ki 5,000 seats actually available nahi thi
- Result: Refund processing, customer anger, brand damage, aur compliance penalties

Yeh sirf "concurrent write" ka case nahi hai. Yeh **business-critical consistency, distributed coordination, retry safety, aur user experience** ka combined challenge hai. Booking systems mein "eventual consistency" kabhi kaam nahi karta. Yahan **strong consistency + graceful degradation** mandatory hai.

Is article mein hum isko zero-to-hero level pe cover karenge:
- Read-Check-Update anti-pattern aur kyun yeh production mein fail hota hai
- Database-level solutions: Atomic updates, `SELECT FOR UPDATE`, `SKIP LOCKED`
- Distributed locking: Redis, Lease mechanisms, Redlock reality check
- Idempotency: Network retries, payment callbacks, aur deduplication patterns
- Hold/Reserve/Release pattern: Industry standard flow
- Real-world architectures: Movie, Flight, Event booking
- Interview traps, anti-patterns, production checklist

Chalo, step-by-step dive karte hain. 🔍

## 🔍 1. Core Problem: Read-Check-Update Anti-Pattern & CAP Implications

Double booking ka root cause 90% cases mein yeh hota hai:
```java
// ❌ ANTI-PATTERN: Read → Check → Update (Not Atomic)
Seat seat = seatRepository.findById(seatId); // Thread A reads: status = AVAILABLE
// Thread B reads: status = AVAILABLE (same time)
if (seat.getStatus() == AVAILABLE) {
    seat.setStatus(BOOKED);
    seatRepository.save(seat); // Both succeed → DOUBLE BOOKING
}
```

### 📊 Why This Happens?
| Layer | Problem | Impact |
|-------|---------|--------|
| **Application** | Gap between `SELECT` and `UPDATE` → race condition window | Multiple threads pass `if` check simultaneously |
| **Database** | Default isolation (`READ COMMITTED`) allows concurrent reads | No serialization of booking attempts |
| **Network** | Retries, timeouts, load balancer re-routing → duplicate requests | Same user booked twice |
| **Architecture** | Microservices, async payments, separate inventory service | Distributed race conditions, inconsistent state |

### ⚖️ CAP Theorem in Booking Context:
- **CP (Consistency + Partition Tolerance):** Booking confirm hone tak system wait karega. Safe, lekin latency high. (Banking, Flights)
- **AP (Availability + Partition Tolerance):** Fast response, but risk of overbooking. Compensation logic needed. (Event ticketing with oversell allowance)
- **Reality:** Most modern booking systems use **CP for inventory + AP for UI/queue**, with explicit fallbacks.

👉 **Rule:** Booking path pe `SELECT → if → UPDATE` kabhi mat likho. Atomicity ya distributed coordination mandatory hai.

## 🗄️ 2. Database-Level Solutions: Atomic Updates & Row Locks

Database native locking sabse reliable baseline hai. Microservices ho ya monolith, DB ko source of truth maanna padta hai.

### ✅ Pattern 1: Atomic UPDATE with Condition
```sql
-- Single query, DB engine ensures atomicity
UPDATE seats 
SET status = 'BOOKED', 
    booked_by = :userId, 
    booked_at = NOW(), 
    version = version + 1
WHERE seat_id = :seatId 
  AND status = 'AVAILABLE' 
  AND version = :currentVersion;

-- Affected rows = 1 → success, 0 → already booked
```
**Pros:** No explicit lock, fast, DB handles contention.  
**Cons:** Application ko retry logic handle karna padta hai.

### 🔒 Pattern 2: Pessimistic Row Lock (`SELECT FOR UPDATE`)
```sql
BEGIN TRANSACTION;
SELECT * FROM seats WHERE seat_id = :id FOR UPDATE; -- Blocks other writers
-- Validate business rules, calculate price, etc.
UPDATE seats SET status = 'BOOKED' WHERE seat_id = :id;
COMMIT;
```
**Pros:** Strong consistency, predictable behavior.  
**Cons:** Blocks concurrent attempts → timeout/retry needed. Connection pool exhaustion risk.

### 🚀 Pattern 3: `SKIP LOCKED` for High-Throughput Queues
```sql
-- Useful for worker-based booking processing
UPDATE seats 
SET status = 'PROCESSING', worker_id = :workerId
WHERE status = 'AVAILABLE'
ORDER BY created_at ASC
LIMIT 1
SKIP LOCKED;
```
**Pros:** Workers pick next available seat without waiting. Great for async processing.  
**Cons:** Not for sync user-facing flows. Requires careful error handling if worker fails.

### 📊 DB Lock Tuning Checklist:
| Parameter | Recommended Value | Rationale |
|-----------|-------------------|-----------|
| `innodb_lock_wait_timeout` / `lock_timeout` | 3-5 seconds | Fail fast, don't hang user |
| Connection pool size | 20-50 (tuned per service) | Avoid pool exhaustion during spikes |
| Transaction scope | Minimal (only booking logic) | Long transactions → lock contention |
| Indexing | `(seat_id, status)` composite index | Fast lock acquisition, full table scan avoid karo |

## 🔐 3. Distributed Locking: Redis, Lease & Reality Check

Jab inventory service alag ho, payment service alag ho, aur DB cross-service locking impractical ho → distributed locks aate hain.

### 🧱 Redis `SETNX` + `EXPIRE` (Basic)
```redis
SET booking:seat:1001 "user:55" NX EX 30
# Returns 1 if set, 0 if exists
```
**Problem:** Network partition → client crashes → lock never released → permanent block.

### 🔄 Lease-Based Locking (Industry Standard)
```java
String lockKey = "lock:seat:" + seatId;
String lockValue = UUID.randomUUID().toString(); // Ownership proof

// Acquire with TTL
Boolean acquired = redisTemplate.opsForValue().setIfAbsent(lockKey, lockValue, Duration.ofSeconds(10));

if (Boolean.TRUE.equals(acquired)) {
    try {
        // Start watchdog thread to renew lease
        scheduledExecutor.scheduleAtFixedRate(() -> {
            // Lua script: only renew if still owned by this client
            String script = "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('EXPIRE', KEYS[1], ARGV[2]) else return 0 end";
            redisTemplate.execute(new DefaultRedisScript<>(script, Long.class), List.of(lockKey), lockValue, 10);
        }, 3, 3, TimeUnit.SECONDS);
        
        return performBooking();
    } finally {
        // Release only if still owned
        String releaseScript = "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end";
        redisTemplate.execute(new DefaultRedisScript<>(releaseScript, Long.class), List.of(lockKey), lockValue);
    }
} else {
    throw new BookingConflictException("Seat already being processed");
}
```

### ⚠️ Redlock Reality Check:
- Martin Kleppmann (Redlock creator) aur distributed systems experts ka consensus: **Redlock production mein risky hai**.
- Clock skew, GC pauses, network partitions → false safety.
- **Better Alternative:** Single Redis cluster + Lua atomicity + DB as source of truth + idempotency. Ya PostgreSQL `pg_advisory_lock` / `SKIP LOCKED`.

### 📋 Distributed Lock Scope Design:
| Scope | Use Case | Lock Key Format |
|-------|----------|-----------------|
| **Per Seat** | Exact seat selection | `lock:seat:{seatId}` |
| **Per Session/User** | Prevent double booking by same user | `lock:user:{userId}:booking` |
| **Per Event/Show** | Global inventory check | `lock:event:{eventId}:inventory` |
| **Per Payment** | Idempotent charge retry | `lock:payment:{paymentIntentId}` |

👉 **Rule:** Distributed lock = coordination tool, not consistency guarantee. Always validate against DB as final source of truth.

## 🔄 4. Idempotency & Safe Retries: Network Ka Sach

Booking systems mein **at-least-once delivery** common hai. Payment gateway timeout, network glitch, load balancer retry → same request 2-3 baar aa sakta hai. Agar system idempotent nahi hai → double charge/double booking.

### 🔑 Idempotency Key Pattern:
1. Client generates `Idempotency-Key: UUID` per booking attempt
2. Server stores key + response/status in dedup table
3. Duplicate request → return cached response without re-executing business logic

```java
@PostMapping("/book")
public ResponseEntity<?> bookSeat(
    @RequestHeader("Idempotency-Key") String idemKey,
    @RequestBody BookingRequest req) {
    
    // Check if already processed
    Optional<BookingResponse> cached = idempotencyStore.get(idemKey);
    if (cached.isPresent()) {
        return ResponseEntity.ok(cached.get());
    }
    
    // Acquire lock / DB transaction
    try {
        BookingResponse response = bookingService.execute(req);
        idempotencyStore.put(idemKey, response, Duration.ofHours(24));
        return ResponseEntity.ok(response);
    } catch (Exception e) {
        idempotencyStore.putError(idemKey, e.getMessage());
        throw e;
    }
}
```

### 🗃️ Dedup Table Schema:
```sql
CREATE TABLE booking_idempotency (
    idempotency_key VARCHAR(64) PRIMARY KEY,
    request_hash VARCHAR(64),
    response_payload JSONB,
    status VARCHAR(20), -- SUCCESS, FAILED, PROCESSING
    created_at TIMESTAMP DEFAULT NOW(),
    UNIQUE (request_hash) -- Optional: prevent identical retries
);
```

### 💳 Payment Callback Idempotency:
- Payment gateway `POST /webhook/payment-success` → multiple retries possible
- Store `payment_intent_id` + `booking_id` mapping
- Use `UPDATE bookings SET status='CONFIRMED' WHERE payment_intent_id=? AND status='PENDING'`
- Affected rows = 1 → process confirmation. 0 → already handled.

👉 **Rule:** External system ke saath har interaction idempotent hona chahiye. Network fail karega, system ko gracefully handle karna chahiye.

## 🎟️ 5. Hold/Reserve/Release Pattern: The Industry Standard

Sync booking + immediate payment = risky (payment gateway timeout → seat stuck or double booked).  
Modern systems use **Temporary Hold → Payment → Confirm/Release** flow.

### 🔄 Flow Architecture:
```
User clicks Book → Seat status = HOLD (TTL: 10 mins) → Show Payment UI
   ↓
Payment Success → Status = CONFIRMED → Send Ticket
   ↓
Payment Timeout/Fail → Status = AVAILABLE (after TTL expiry)
```

### 💻 Implementation (Redis + DB Sync):
```java
public void holdSeat(String seatId, String userId) {
    String holdKey = "hold:seat:" + seatId;
    String result = redisTemplate.opsForValue().setIfAbsent(holdKey, userId, Duration.ofMinutes(10));
    
    if (!"OK".equals(result)) {
        throw new SeatUnavailableException("Seat already held");
    }
    
    // Async DB sync (outbox/event)
    eventPublisher.publish(new SeatHeldEvent(seatId, userId, Instant.now().plus(Duration.ofMinutes(10))));
}

// Background worker: Release expired holds
@Scheduled(fixedRate = 60000)
public void releaseExpiredHolds() {
    // Scan Redis keys or query DB for expired holds
    // SET status = AVAILABLE WHERE status = HOLD AND expires_at < NOW()
}
```

### ⚖️ Trade-offs:
| Aspect | Benefit | Cost |
|--------|---------|------|
| **Better UX** | User gets time to enter payment details | Inventory temporarily reduced |
| **Consistency** | Payment failure = auto release | Requires cleanup workers, TTL management |
| **Scalability** | Async confirmation decouples payment | Eventual consistency window |

👉 **Rule:** Hold TTL = payment gateway avg completion time + buffer (usually 5-15 mins). Never make it infinite.

## 🌐 6. Real-World Architectures: Movie, Flight, Events

### 🎬 Scenario 1: Movie Theater Booking (Seat Map UI)
**Challenge:** Visual seat selection, 1000+ concurrent users, instant feedback.

**Architecture:**
- Frontend: Fetch seat map from cache (Redis)
- Click seat → `POST /hold` → Redis `SETNX` + TTL 10m → UI turns yellow
- Payment → `POST /confirm` → DB atomic update → status = BOOKED → email ticket
- Timeout → WebSocket pushes "Seat Released" → UI refreshes
- Anti-fraud: Rate limit per IP/user, CAPTCHA on high-demand shows

### ✈️ Scenario 2: Airline Booking (GDS + Fare Rules)
**Challenge:** Complex pricing, multi-city, overbooking allowance, GDS latency.

**Architecture:**
- Inventory CP system (strong consistency)
- Fare lock service: Lock price for 20 mins (`price_hold` table)
- GDS sync: Async queue, retry with idempotency keys
- Overbooking: ML-based cancellation prediction → intentionally oversell by X%
- Compliance: Audit trail for every status change (regulatory requirement)

### 🎤 Scenario 3: Concert/Event Flash Sale
**Challenge:** 100k users, 20k seats, 30-second sellout, DDoS-like traffic.

**Architecture:**
- Virtual Waiting Room (Cloudflare/Custom): Queue users, release in batches
- Token-based booking: Only queued users get booking token
- Redis inventory decrement (Lua script) → fast, atomic
- DB sync worker → eventual consistency, but Redis is source for UI
- Fallback: "Sold Out" state cached for 5 mins to prevent DB hammering

## ⚠️ 8. Anti-Patterns & Production Gotchas

| Anti-Pattern | Why It's Bad | Fix |
|--------------|--------------|-----|
| `SELECT → if → UPDATE` in application code | Race condition window → double booking | Use atomic DB updates or explicit row locks |
| Long-running DB transactions during booking | Lock holds → pool exhaustion → cascade failure | Minimize transaction scope, validate before lock, async heavy ops |
| Missing idempotency on payment/webhook callbacks | Double charge, duplicate bookings | Dedup table + idempotency key + unique constraints |
| Infinite lock TTL or missing cleanup | Permanent seat block, inventory leak | Lease renewal + watchdog + background expiry worker |
| Relying solely on application cache for inventory | Cache-DB inconsistency → overselling | Cache as read-through, DB as source of truth, Lua atomic decrement |
| Hardcoding "Sold Out" without cooldown | DB hammered even after sellout | Cache sold-out state with TTL, circuit breaker on inventory queries |

## 🧰 9. Production-Ready Checklist

✅ Atomic booking operation: `UPDATE ... WHERE status = AVAILABLE` or `SELECT FOR UPDATE`  
✅ Idempotency keys implemented for all external-facing endpoints & webhooks  
✅ Hold/Reserve/Release flow with configurable TTL (5-15 mins)  
✅ Background worker for expired hold cleanup + audit logging  
✅ Redis distributed locks use lease renewal + ownership validation + Lua atomicity  
✅ Payment integration idempotent: `payment_intent_id` mapping + status checks  
✅ Load testing: Simulate 5-10x peak concurrency, measure double booking rate (should be 0)  
✅ Monitoring: Lock wait time, hold expiry count, idempotency hit rate, inventory sync lag  
✅ Fallback paths: Cache sold-out state, circuit breaker on DB/Redis, graceful degradation  
✅ Documentation: Booking flow diagram, lock scopes, TTL values, idempotency contract recorded

## 📝 Summary & Key Takeaways

Multiple users booking the same seat simultaneously ek **distributed consistency + business reliability** challenge hai. Ise handle karne ke liye:

1. **Atomicity First:** `SELECT → if → UPDATE` kabhi mat likho. DB atomic updates ya explicit locks use karo.
2. **Distributed Coordination Smartly:** Redis lease locks + Lua scripts + DB validation. Redlock/complex consensus avoid karo unless absolutely necessary.
3. **Idempotency is Non-Negotiable:** Network fail karega, retries aayenge, webhooks duplicate honge. Idempotency keys + dedup tables mandatory hain.
4. **Hold/Reserve/Release Pattern Adopt Karo:** Sync booking + immediate payment risky hai. Temporary hold + TTL + async confirmation = industry standard.
5. **Measure & Fail Gracefully:** Double booking rate, lock contention, hold expiry, inventory sync lag → inke bina aap blind fly kar rahe ho. Circuit breakers, cached states, aur fallback flows design karo.

Backend interviews aur system design rounds mein interviewer dekhna chahta hai ki aap:
- Booking flow ke end-to-end consistency requirements samajhte hain
- DB locking, distributed coordination, aur idempotency ko practically integrate kar sakte hain
- CAP theorem ko business context ke saath map kar sakte hain
- Production debugging, monitoring, aur graceful degradation mindset rakhte hain
