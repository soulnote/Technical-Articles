# What if GPU Queue Starvation Happens?
## Fair Scheduling, Priority Queues, Batch Optimization & GPU Resource Management

### 🎯 Introduction: Jab "High-Priority Request" Queue Mein Hamesha Ke Liye Phans Jaye

AI/ML inference systems ka ek subtle lekin dangerous problem: **GPU Queue Starvation**.

Socho aapka platform multiple types of inference requests handle karta hai:
- 🔴 **Critical:** Real-time fraud detection (<50ms SLA)
- 🟡 **Standard:** Product recommendations (<200ms SLA)  
- 🟢 **Background:** Batch analytics, model retraining (flexible SLA)

Agar scheduling properly design nahi kiya gaya, toh:
- Background jobs queue mein accumulate hote rehte hain
- Unke large batch sizes GPU memory occupy karte hain
- Critical requests ko GPU slots nahi milte → SLA breach
- "Priority inversion": Low-priority tasks high-priority ko block karte hain
- User experience degrade, business impact, revenue loss

Yeh sirf "queue management" ka issue nahi hai. Yeh **fair scheduling algorithms, priority-aware resource allocation, batch size tuning, aur preemption strategies** ka combined systems engineering challenge hai.

## 🔍 1. Core Problem: GPU Queue Starvation Kyu Hota Hai?

GPU queue starvation tab hota hai jab certain requests **indefinitely wait** karte hain GPU resources ke liye, jabki system technically "busy" hai lekin unke liye progress nahi kar raha.

### 📊 Common Starvation Triggers:
| Trigger | Mechanism | Impact |
|---------|-----------|--------|
| **Priority Inversion** | Low-priority large batches hold GPU while high-priority small requests wait | Critical SLA breach, user-facing failures |
| **Batch Size Imbalance** | Large batches (256) consume GPU longer than small batches (8) → small requests starve | Throughput high, but latency unfair |
| **Resource Fragmentation** | GPU memory fragmented → can't fit new batch even if compute available | Under-utilization + starvation combo |
| **No Preemption** | Running job can't be interrupted → high-priority must wait for completion | Worst-case latency = longest job duration |
| **Unfair Queue Discipline** | FIFO/FCFS allows head-of-line blocking | First slow job blocks everyone behind |

### 📈 Starvation Detection Metrics:
```yaml
starvation.metrics:
  wait_time_p99_by_priority:
    critical: alert > 100ms
    standard: alert > 500ms
    background: alert > 10s
  queue_depth_ratio:
    # If background queue 100x critical queue → imbalance
    alert if background_depth / critical_depth > 50
  gpu_idle_with_pending:
    # GPU idle but requests waiting = fragmentation issue
    alert if gpu_util < 30% AND queue_depth > 100
  priority_inversion_events:
    # Count of high-priority waiting while low-priority running
    alert if count > 0 for 1m
```

👉 **Rule:** Starvation ko "rare edge case" mat maano. Multi-tenant, multi-priority AI systems mein yeh **expected behavior** hai. Design-time pe prevent karo.

## ⚖️ 2. Fair Scheduling Algorithms: Theory to Implementation

Fair scheduling ka goal: **Resources ko priorities, weights, aur SLAs ke hisaab se allocate karna**, taaki koi request class permanently starve na ho.

### 🔧 Algorithm Comparison:

| Algorithm | How It Works | Best For | Complexity |
|-----------|--------------|----------|------------|
| **FIFO (First-In-First-Out)** | Simple queue, first come first served | Single-priority, homogeneous workloads | O(1) |
| **Priority Queue** | Higher priority requests served first | Clear priority tiers, preemption possible | O(log n) |
| **Weighted Fair Queuing (WFQ)** | Each class gets bandwidth proportional to weight | Multi-tenant, guaranteed minimum shares | O(log n) |
| **Deficit Round Robin (DRR)** | Round-robin with byte/packet deficit counters | Variable-size batches, fair throughput | O(1) amortized |
| **Dominant Resource Fairness (DRF)** | Fairness across multiple resources (GPU mem, compute, bandwidth) | Heterogeneous workloads, multi-resource clusters | O(n log n) |

### 💻 Priority Queue Implementation (Java):
```java
public class PriorityInferenceQueue {
    private final PriorityQueue<InferenceRequest>[] priorityQueues;
    private static final int NUM_PRIORITIES = 3; // CRITICAL, STANDARD, BACKGROUND
    
    @SuppressWarnings("unchecked")
    public PriorityInferenceQueue() {
        priorityQueues = new PriorityQueue[NUM_PRIORITIES];
        for (int i = 0; i < NUM_PRIORITIES; i++) {
            priorityQueues[i] = new PriorityQueue<>(Comparator.comparingLong(InferenceRequest::getArrivalTime));
        }
    }
    
    public void enqueue(InferenceRequest request) {
        int priority = request.getPriority().ordinal();
        priorityQueues[priority].offer(request);
    }
    
    public List<InferenceRequest> dequeueBatch(int maxBatchSize, long maxWaitMs) {
        List<InferenceRequest> batch = new ArrayList<>();
        long deadline = System.currentTimeMillis() + maxWaitMs;
        
        // Priority order: CRITICAL → STANDARD → BACKGROUND
        for (int priority = 0; priority < NUM_PRIORITIES && batch.size() < maxBatchSize; priority++) {
            PriorityQueue<InferenceRequest> queue = priorityQueues[priority];
            
            while (!queue.isEmpty() && batch.size() < maxBatchSize) {
                InferenceRequest req = queue.peek();
                
                // Check if request has waited too long (aging)
                if (System.currentTimeMillis() - req.getArrivalTime() > maxWaitMs) {
                    // Promote to higher priority implicitly by taking it
                    batch.add(queue.poll());
                } else if (System.currentTimeMillis() >= deadline) {
                    break; // Time to form batch
                } else {
                    break; // Higher priority queue still has fresh requests
                }
            }
        }
        return batch;
    }
}
```

### 🔄 Aging Mechanism (Prevent Starvation):
```java
// Background request that waited too long gets "priority boost"
public class AgingPriorityCalculator {
    private static final long AGING_THRESHOLD_MS = 5000;
    private static final int PRIORITY_BOOST = 1; // Move up one level
    
    public int getEffectivePriority(InferenceRequest request) {
        int basePriority = request.getPriority().ordinal();
        long waitTime = System.currentTimeMillis() - request.getArrivalTime();
        
        if (waitTime > AGING_THRESHOLD_MS) {
            // Boost priority (but don't exceed CRITICAL)
            return Math.max(0, basePriority - PRIORITY_BOOST);
        }
        return basePriority;
    }
}
```

👉 **Rule:** Pure priority queues can starve low-priority tasks. **Aging** (priority boost over time) ya **weighted fair queuing** use karo taaki sabko progress mile.

## 🎯 3. Priority Queue Design: Multi-Level Queues & Preemption

Production systems mein simple priority queues kaafi nahi hote. Advanced patterns chahiye.

### 🏗️ Multi-Level Feedback Queue (MLFQ) Pattern:
```
Level 0 (CRITICAL): 
  - Max batch: 8
  - Timeout: 10ms
  - Preempts lower levels
  
Level 1 (STANDARD):
  - Max batch: 32
  - Timeout: 50ms
  - Runs when Level 0 empty
  
Level 2 (BACKGROUND):
  - Max batch: 128
  - Timeout: 500ms
  - Runs only when higher levels empty
  - Subject to preemption
```

### 💻 Preemption Implementation:
```python
class PreemptiveGPUScheduler:
    def __init__(self, gpu_manager):
        self.gpu_manager = gpu_manager
        self.running_jobs = {}  # job_id -> JobInfo
        
    def schedule(self, pending_requests):
        # Check if critical request waiting
        critical_waiting = [r for r in pending_requests if r.priority == Priority.CRITICAL]
        
        if critical_waiting and self._has_lower_priority_running():
            # Preempt: Find lowest priority running job
            victim = self._find_preemption_victim()
            if victim and victim.can_checkpoint():
                # Save state, free GPU
                victim.checkpoint()
                self.gpu_manager.release(victim.gpu_id)
                self.running_jobs.pop(victim.job_id)
                
                # Schedule critical request
                return self._batch_and_schedule(critical_waiting)
        
        # Normal scheduling
        return self._batch_and_schedule(pending_requests)
    
    def _find_preemption_victim(self):
        # Prefer: background priority, checkpointable, longest remaining time
        candidates = [j for j in self.running_jobs.values() 
                     if j.priority == Priority.BACKGROUND and j.can_checkpoint()]
        return max(candidates, key=lambda j: j.estimated_remaining_time, default=None)
```

### ⚠️ Preemption Trade-offs:
| Benefit | Cost | Mitigation |
|---------|------|------------|
| Critical requests get immediate GPU | Preempted job loses progress | Checkpointing, incremental save, resume capability |
| SLA compliance for high-priority | Throughput may decrease | Limit preemption frequency, use partial preemption |
| Fair resource allocation | Complexity in job management | Clear preemption policies, monitoring, alerting |

👉 **Rule:** Preemption powerful hai lekin expensive. Sirf **critical vs background** scenarios mein use karo. Checkpointing support mandatory hai.

## 🧮 4. Batch Optimization: Smart Sizing & GPU Memory Management

Batch size directly impacts starvation: large batches = longer GPU hold time = more waiting for others.

### 🔍 Dynamic Batch Sizing Algorithm:
```python
class DynamicBatchSizer:
    def __init__(self, gpu_memory_gb, model_memory_gb, target_latency_ms):
        self.gpu_memory_gb = gpu_memory_gb
        self.model_memory_gb = model_memory_gb
        self.target_latency_ms = target_latency_ms
        self.history = []  # Track latency vs batch_size
        
    def compute_optimal_batch(self, pending_requests, current_gpu_load):
        # Available memory for activations
        available_memory = self.gpu_memory_gb - self.model_memory_gb - current_gpu_load
        
        # Estimate memory per request (simplified)
        memory_per_request = 0.1  # GB, model-specific
        
        # Max batch by memory
        max_by_memory = int(available_memory / memory_per_request)
        
        # Max batch by latency (empirical model)
        # latency ≈ base_latency + k * batch_size
        max_by_latency = int((self.target_latency_ms - 10) / 2)  # Example formula
        
        # Consider priority mix
        critical_count = sum(1 for r in pending_requests if r.priority == Priority.CRITICAL)
        
        # Prefer smaller batches if critical requests waiting
        if critical_count > 0:
            target_batch = min(8, max_by_latency, max_by_memory)
        else:
            target_batch = min(32, max_by_latency, max_by_memory)
        
        return min(len(pending_requests), target_batch)
```

### 🗂️ Bin Packing for GPU Memory:
```python
# GPU memory fragmentation problem:
# Batch A: 2GB, Batch B: 2GB, GPU: 4GB total
# If A loads first, B can't fit even though 2GB free (fragmented)

class FragmentationAwareScheduler:
    def __init__(self, gpu_memory_gb):
        self.gpu_memory_gb = gpu_memory_gb
        self.allocated = []  # List of (start, end) memory ranges
        
    def can_fit(self, required_memory_gb):
        # First-fit or best-fit allocation
        free_ranges = self._compute_free_ranges()
        return any(size >= required_memory_gb for _, size in free_ranges)
    
    def _compute_free_ranges(self):
        # Merge allocated ranges, find gaps
        if not self.allocated:
            return [(0, self.gpu_memory_gb)]
        
        sorted_alloc = sorted(self.allocated)
        free = []
        current = 0
        
        for start, end in sorted_alloc:
            if start > current:
                free.append((current, start - current))
            current = max(current, end)
        
        if current < self.gpu_memory_gb:
            free.append((current, self.gpu_memory_gb - current))
        
        return free
```

### 📊 Batch Size vs Performance Trade-off:
| Batch Size | GPU Utilization | Latency p99 | Throughput (req/sec) | Best Use Case |
|------------|----------------|-------------|---------------------|---------------|
| **1-8** | 30-50% | 20-50ms | Low | Critical, real-time inference |
| **16-32** | 60-80% | 50-150ms | Medium | Standard user-facing features |
| **64-128** | 80-95% | 150-400ms | High | Background processing, analytics |
| **256+** | 90-98% | 400ms+ | Very High | Offline batch jobs, training |

👉 **Rule:** Batch size ko **static mat rakho**. Priority mix, GPU load, aur SLA ke basis pe dynamic adjust karo.

### 🔄 Ray Serve for Dynamic Scheduling:
```python
from ray import serve

@serve.deployment(num_replicas=2, ray_actor_options={"num_gpus": 0.5})
class InferenceActor:
    def __init__(self, model_name, priority):
        self.model = load_model(model_name)
        self.priority = priority  # Used for scheduling
    
    async def __call__(self, request):
        return await self.model.infer_async(request)

# Router with priority-aware batching
@serve.deployment
class PriorityRouter:
    def __init__(self):
        self.critical = InferenceActor.bind("fraud-detect", priority="critical")
        self.standard = InferenceActor.bind("recommendations", priority="standard")
        self.background = InferenceActor.bind("analytics", priority="background")
    
    async def __call__(self, request):
        if request.priority == "critical":
            return await self.critical(request)
        elif request.priority == "background":
            return await self.background(request)
        else:
            return await self.standard(request)
```

## ⚠️ 7. Anti-Patterns & Production Gotchas

| Anti-Pattern | Why It's Dangerous | Fix |
|--------------|-------------------|-----|
| **FIFO queue for mixed priorities** | Head-of-line blocking, critical requests starve | Priority queue + aging mechanism |
| **Static large batch sizes** | Long GPU hold times, unfair latency distribution | Dynamic batch sizing based on priority mix + SLA |
| **No preemption for critical workloads** | Worst-case latency = longest background job | Implement checkpointing + selective preemption |
| **Ignoring GPU memory fragmentation** | GPU appears idle but can't fit new batches | Bin-packing scheduler, memory defragmentation, MIG partitions |
| **Over-preempting** | Background jobs never complete, throughput drops | Limit preemption frequency, use partial preemption, priority thresholds |
| **No visibility into queue state** | Starvation detected too late (after SLA breach) | Real-time metrics: wait time by priority, queue depth ratios, inversion events |

## 📝 Summary & Key Takeaways

GPU queue starvation ek **resource allocation fairness** problem hai, na ki simple capacity issue. Ise handle karne ke liye:

1. **Priority Queues + Aging:** Simple priority queues low-priority tasks ko starve kar sakte hain. Aging (priority boost over time) ya weighted fair queuing se sabko progress mile.
2. **Dynamic Batch Sizing:** Static large batches GPU ko long time ke liye occupy karte hain. Priority mix aur SLA ke basis pe batch size dynamically adjust karo.
3. **Preemption with Checkpointing:** Critical requests ke liye GPU chahiye? Lower-priority running job ko checkpoint karke preempt karo. Lekin iska cost samjho aur frequency limit karo.
4. **Fragmentation-Aware Allocation:** GPU memory fragmented hone se naye batches fit nahi hote. Bin-packing algorithms ya NVIDIA MIG se memory efficiently manage karo.
5. **Tiered GPU Pools:** Critical, standard, background workloads ke liye alag GPU pools. Isolation + fairness + cost optimization ek saath.
6. **Observability is King:** Wait time by priority, inversion events, fragmentation metrics — inke bina starvation blind hai.

Backend interviews, ML platform engineering, aur production AI systems design mein interviewer dekhna chahta hai ki aap:
- GPU scheduling challenges ko traditional CPU scheduling se alag samajhte hain
- Fairness algorithms (WFQ, DRF, aging) ko practical context mein apply kar sakte hain
- Preemption, checkpointing, aur batch optimization ke trade-offs jaante hain
- "Fair but efficient" scheduling mindset rakhte hain
