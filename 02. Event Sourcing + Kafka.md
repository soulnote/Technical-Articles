#  Event Sourcing + Kafka


##  1. Core Mindset Shift: Timeline vs Snapshot

###  Traditional Database Soch (State-Centric)
```
❌ "Current state kya hai?"
 Example: `UPDATE parcels SET status='DELIVERED' WHERE id='P123';`
```
- Har naya update **purane data ko overwrite** kar deta hai
- History gayab → sirf "aaj ka status" bachta hai
- Debugging = guesswork + logs dhundhna

###  Event Sourcing Soch (Fact-Centric)
```
 "Kaun-se events is state tak le aaye?"
 Example: `INSERT INTO event_log VALUES ('P123', 'BOOKED', 'Jabalpur', t1);`
                `INSERT INTO event_log VALUES ('P123', 'DISPATCHED', 'Nagpur', t2);`
                `INSERT INTO event_log VALUES ('P123', 'DELAYED', '18h', t3);`
                `INSERT INTO event_log VALUES ('P123', 'DELIVERED', 'Pune', t4);`
```
- Har event ek **immutable fact** hai (jo ho gaya, wo ho gaya)
- Kuch bhi overwrite/delete nahi hota → sirf **append**
- Current state = sabhi past events ko sequence mein replay karke nikala jata hai

>  **Bank Statement Analogy**: Tumhara bank balance sirf ek number nahi hota. Wo `credit`, `debit`, `refund`, `charge` events ka sum hai. Event Sourcing wahi karta hai software ke liye.

##  2. How It Works Under the Hood

###  Event Structure (Production-Ready)
```java
public abstract class ParcelEvent {
    public final String eventId;      // UUID (idempotency ke liye)
    public final String parcelId;
    public final Instant occurredAt;  // Jab event actually hua
    public final Map<String, Object> context; // Location, hub, agentId, etc.
}

// Concrete examples
class ParcelBookedEvent extends ParcelEvent { /* ... */ }
class ParcelDispatchedEvent extends ParcelEvent { /* ... */ }
class ParcelDelayedEvent extends ParcelEvent { /* ... */ }
class ParcelDeliveredEvent extends ParcelEvent { /* ... */ }
```

###  State Reconstruction (The "Replay Engine")
```java
public ParcelState reconstruct(String parcelId) {
    List<ParcelEvent> events = eventStore.getEvents(parcelId); // Sorted by occurredAt
    
    ParcelState state = new ParcelState();
    state.setId(parcelId);
    
    for (ParcelEvent e : events) {
        if (e instanceof ParcelBookedEvent) state.setStatus("BOOKED");
        else if (e instanceof ParcelDispatchedEvent) state.setStatus("IN_TRANSIT");
        else if (e instanceof ParcelDelayedEvent) state.addDelay(e);
        else if (e instanceof ParcelDeliveredEvent) state.setStatus("DELIVERED");
        // ... aur bhi events
    }
    return state;
}
```
>  **Rule**: State kabhi directly update nahi hoti. Hamesha events se derive hoti hai.  
> ⚡ **Time-Travel Possible**: `reconstruct(parcelId, Instant.parse("2024-01-15T14:00:00Z"))` → kal shaam kahan tha? Pata chal jayega.

##  3. Real Problems → Event Sourcing Solutions

###  Problem 1: "Parcel 2 din late kyun aaya?" (Root Cause Debugging)
| Traditional Approach | Event-Sourced Approach |
|----------------------|------------------------|
| Logs scattered across servers, Kibana pe filter karna padta hai | Single timeline: `Booked → Dispatched → Nagpur (18h stall) → Missed truck → Next day dispatch` |
| Blame game: "Warehouse team ne nahi bheja" | Exact pin: `ParcelDelayedEvent` at `Nagpur Hub`, `timestamp`, `reason="truck_misroute"` |
| Fix: Guesswork + manual check | Fix: Optimize Nagpur routing, add alert on `delay > 6h` |

```java
// Analytics: Delay hotspots dhundho
Map<String, Long> delayCount = eventStore.stream()
    .filter(e -> e instanceof ParcelDelayedEvent)
    .map(e -> e.getLocation())
    .collect(groupingBy(loc -> loc, counting()));
// Output: {"Nagpur": 142, "Mumbai": 18, "Delhi": 7}
// → Nagpur hub pe infrastructure upgrade karo
```

###  Problem 2: Ek Event → Multiple Systems (Loose Coupling)
```
 Event: ParcelArrivedEvent("Pune", t)
       │
       ├─▶  Tracking UI → "Out for delivery" show karo
       ├─▶  SMS/Email Service → Customer ko notify karo
       ├─▶  Analytics → SLA compliance calculate karo
       ├─▶  ML Model → Future delay prediction update karo
       └─▶  Support Bot → Agent dashboard refresh karo
```
**Traditional Pain**: Har service ko directly call karna → tight coupling, cascade failure, retry hell  
**Event Sourcing + Kafka**: Publish once, subscribe many. Services independent. Failure isolate hoti hai.

###  Problem 3: System Crash ya Naya Feature Add Karna
**Scenario**: 2 saal baad naya service bana hai jo `"average transit time per route"` calculate karega.
- ❌ Traditional: Purane DB schema migrate karo, data loss risk, downtime
-  Event Sourcing: Purane events ko **naye logic ke saath replay karo**. Zero migration. Zero data loss.
```java
// Naya service, purane data pe kaam karega
public RouteMetrics computeMetrics() {
    return eventStore.getAllEvents("parcel-events")
        .filter(e -> e.getType().isTransitRelated())
        .groupingBy(RouteExtractor::extract)
        .mapping(TransitTimeCalculator::compute, toList());
}
```

##  4. Kafka: Event Sourcing ka Real-Time Highway

Kafka koi simple message queue nahi hai. Ye ek **distributed, append-only, ordered event log** hai jo Event Sourcing ke liye perfect fit hai.

###  Kafka Architecture (Simplified)
```
[Parcel Service] → publish → Kafka Topic: "parcel-events"
                                   │
                   ┌───────────────┼───────────────┐
                   ▼               ▼               ▼
           [Tracking Svc]    [Notification Svc]  [Analytics Svc]
           (Consumer Group A) (Group B)          (Group C)
```

###  Key Kafka Concepts (Hinglish Explanation)
| Concept | Kya Hai? | Kyu Zaroori Hai? |
|---------|----------|------------------|
| **Topic** | Ek category ka event stream (e.g., `parcel-events`) | Events ko logically separate karta hai |
| **Partition** | Topic ko parallel chunks mein divide karna | Scale + ordered processing within partition |
| **Offset** | Har event ka sequential number | Replay, resume, exactly-once ke liye backbone |
| **Consumer Group** | Multiple services independently same topic consume kar sakein | Loose coupling, independent scaling |
| **Retention** | Events kitne din/store honge | Audit compliance, replay window control |

###  Production Snippet: Idempotent Producer + Consumer
```java
//  Producer: Idempotent + Ordered
kafkaTemplate.send("parcel-events", parcelId, event); 
// partition key = parcelId → same parcel ke events ordered rahenge

//  Consumer: Exactly-Once + Offset Management
@KafkaListener(topics = "parcel-events", groupId = "tracking-svc")
public void handle(ParcelEvent event, @Header(KafkaHeaders.RECEIVED_OFFSET) long offset) {
    // 1. Process event
    updateTrackingState(event);
    // 2. Commit offset manually (auto-commit off in prod)
    kafkaListenerContainer.getContainerProperties().setSyncCommits(true);
}
```
>  **Pro Tip**: Hamesha `partitionKey = aggregateId` (e.g., `parcelId`) rakho. Isse ek parcel ke events hamesha same partition mein jayenge → order preserved.

##  5. Advanced Concepts (Jo Often Confuse Karte Hain)

###  Event Sourcing ≠ CQRS
| Concept | Focus | Kaise Kaam Karta Hai |
|---------|-------|----------------------|
| **Event Sourcing** | **Write/Storage** model | State ko events ke roop mein store karta hai |
| **CQRS** | **Read/Write separation** | Commands (write) aur Queries (read) ke liye alag models/DBs use karta hai |

>  **Best Practice**: Inko sath use karo, lekin alag samjho.  
> Event Store → Write side  
> Read Projections (Elasticsearch, Redis, PostgreSQL) → Query side  
> Events don't change → Read models can be optimized freely.

###  Snapshots: Replay Performance Fix
10,000 events replay karna slow ho sakta hai. Solution:
```java
// Har 500 events pe snapshot save karo
if (eventCount % 500 == 0) {
    snapshotStore.save(parcelId, currentState, eventCount);
}
// Next time: load snapshot → replay only last 49 events
```
>  Performance: `O(N)` → `O(snapshot_interval)`

###  Schema Evolution (Backward Compatibility)
Kal tak `location` tha String, aaj `Location` object ban gaya. Purane events break nahi honge agar:
- Naye fields add karo, purane mat hatao
- Default values provide karo
- Use `Avro/Protobuf + Schema Registry`
```java
// Safe evolution
class ParcelArrivedEvent {
    String location;      // old (keep for compat)
    Location locationObj; // new
    // Deserializer handles both
}
```

###  Idempotency & Exactly-Once Semantics
Network retry hoga → same event do baar aa sakta hai. Handle kaise?
```java
// Consumer side: Duplicate detection
if (eventRepository.existsById(event.getEventId())) {
    log.info("Duplicate event, skipping: {}", event.getEventId());
    return;
}
eventRepository.save(event);
process(event);
```
>  Production mein: Kafka `enable.idempotence=true` + Consumer offset management + Event ID deduplication = Safe pipeline.

##  6. Decision Matrix: Kab Use Karein? Kab Avoid?

 **Use Event Sourcing When:**
- Audit/Compliance mandatory hai (Finance, Healthcare, Logistics, Govt)
- Full history se value milti hai (debugging, analytics, ML, customer trust)
- Multiple independent systems same data pe kaam karte hain
- Business process naturally timeline-based hai (order lifecycle, approval flow, user journey)

❌ **Avoid When:**
- Simple CRUD app (blog, todo, basic CMS)
- Low-latency reads critical hain aur snapshot/replay overhead unacceptable hai
- Team ko event-driven, eventual consistency, ya CQRS ka experience nahi hai
- Storage cost ya log management ka overhead handle nahi kar sakte

4. **Production Checklist**:
   - [ ] Idempotent event IDs
   - [ ] Partition key = aggregate ID
   - [ ] Offset management (manual commit)
   - [ ] Schema versioning + backward compat
   - [ ] Snapshot strategy for large aggregates
   - [ ] Dead Letter Queue (DLQ) for poison events
   - [ ] Monitoring: Lag, Throughput, Error Rate, Replay Time
