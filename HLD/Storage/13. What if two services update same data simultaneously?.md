
## 1. Do Services Ek Saath Update Karein — Asli Matlab Kya Hai?

Jab do alag-alag services (ya threads, instances) ek hi resource (database row, document, key-value pair) ko roughly same time pe modify karne ki koshish karte hain, to **race condition** create hoti hai. Problem yeh hai ki dono ne resource ki current state padhi, independently changes kiye, aur fir dono ne apna result write kar diya. Jo last write successful hoti hai, wo pehle wali update ko overwrite kar deti hai — pehla update **silently lost** ho jaata hai. Isi ko **lost update problem** kehte hain.

Yeh sirf database tak seemit nahi hai; koi bhi shared mutable state (cache, configuration, file) pe ho sakta hai. Distributed nature ki vajah se services ke beech implicit coordination nahi hota, isliye yeh problem aur bhi common hai.

## 2. Real-World Example (Banking Balance Update — Detailed)

Maan lo ek digital wallet app hai. User ke paas `₹10,000` balance hai. Do concurrent operations:
- **Service A:** User ne merchant payment kiya ₹2,000 (deduct).
- **Service B:** User ko cashback mila ₹500 (credit). (Ya dono payments alag merchants ko, par dono ka balance padhna aur update karna ek hi row ko modify karta hai.)

**Flow (without concurrency control):**
1. Service A: `SELECT balance FROM wallets WHERE user_id = 123` → 10,000.
2. Service B: `SELECT balance FROM wallets WHERE user_id = 123` → 10,000 (same time).
3. Service A: Calculate new_balance = 10,000 - 2,000 = 8,000. `UPDATE wallets SET balance = 8000 WHERE user_id = 123`.
4. Service B: Calculate new_balance = 10,000 + 500 = 10,500. `UPDATE wallets SET balance = 10500 WHERE user_id = 123`.

Agar timing aisi rahi ki Service B ka update last execute hua, to final balance `10,500` ho jaayega. Service A ka 2,000 deduction gayab — user ne payment kar diya lekin paise katne ka record nahi bana (ya sirf transaction log mein hai lekin balance galat). User ko lagta hai payment fail hui, merchant ko lagta hai paisa aaya, wallet provider ke paas reconciliation fail. Big financial mess.

## 3. Do Services Simultaneously Update Kyun Kar Dete Hain? (Root Cause Tree)

### 3.1 Shared Mutable State without Coordination
- Do independent services (Payment, Cashback, Order, Inventory) ek hi database table/row pe likh rahe hain, unke beech koi direct communication nahi.
- Microservices architecture mein database per service hona chahiye (pattern), lekin practical systems mein kuch shared tables reh jaati hain.

### 3.2 Read-Modify-Write Cycle (Check-Then-Act)
- Application pehle data padhti hai (SELECT), kuch business logic lagati hai, fir data update karti hai (UPDATE). Yeh non-atomic cycle race condition ke liye vulnerable hai.

### 3.3 Lack of Proper Transaction Isolation
- Database transaction isolation level `READ COMMITTED` (default in many DBs) lost updates allow kar sakta hai agar application `SELECT` and then `UPDATE` kare without explicit locking. Only `REPEATABLE READ` or `SERIALIZABLE` some databases might prevent, but MySQL InnoDB default `REPEATABLE READ` also allows lost updates in certain cases (if you use plain UPDATE without version check, the last one overwrites). Real safety requires optimistic/pessimistic locking.

### 3.4 No Optimistic Locking Mechanism
- Table mein version column nahi, ya update statement version check nahi karta. Blind update se overwrite.

### 3.5 Concurrent Writes from Multiple Threads/Services
- High traffic, retry logic, message queue consumers parallel processing same entity.

### 3.6 Use of External Caching with Write-Behind
- Cache mein update kiya, database baad mein async update; doosra service bhi cache ko update kare, inconsistency.

## 4. Yeh Khatarnak Kyun Hai? (Business Impact)

### 4.1 Financial Loss
- Galat balance, duplicate payments, missing deductions. Jaise upar wala example.

### 4.2 Inventory Overselling
- Do orders same stock decrement karein, ek overwrite doosra, stock count galat, negative inventory ya oversell.

### 4.3 Data Corruption
- Silently missing updates, no one notices until manual reconciliation, data drift.

### 4.4 User Experience Issues
- User ne change save kiya, refresh ke baad wapas purana dikhe (another user's change overwritten).

### 4.5 Compliance Failure
- Financial audit trail incomplete, lost updates detect hote hain to reporting failure.

### 4.6 Cascading Logic Errors
- Wrong balance → subsequent operations fail (e.g., insufficient funds decline legitimate txns).

## 5. Solutions (Concurrency Control Techniques with Examples)

Prateek ne locking aur optimistic locking ki baat ki. Ab hum sab strategies detail mein dekhenge.

### 5.1 Pessimistic Locking (Database-Level)
- Jab Service A record padhna chahti hai, wo `SELECT ... FOR UPDATE` karti hai, transaction ke andar. Isse row pe exclusive lock lag jaata hai. Service B `FOR UPDATE` se padhegi to block hogi jab tak Service A transaction commit/rollback nahi kar deti.
- **Example:** PostgreSQL/MySQL: `SELECT * FROM wallets WHERE user_id = 123 FOR UPDATE`. Inside a transaction. Service A lock, Service B waits. Consistent, but concurrency kam — high contention pe queue lag sakti hai.

### 5.2 Optimistic Locking (Version/ Timestamp)
- Table mein `version` integer column rakho. Update query: `UPDATE wallets SET balance = ?, version = version + 1 WHERE user_id = ? AND version = ?`. Agar version mismatch (koi aur update ho chuka), affected rows = 0, application retry.
- **Example:** JPA `@Version` annotation. Hibernate automatically includes version check. Agar Service B ne beech mein update kar diya, Service A ka update 0 rows affected milega, to `OptimisticLockException` throw, Service A latest data se retry.
- **Retry logic:** Spring Retry ya manual while loop with backoff. Jaise:

```java
@Retryable(value = {OptimisticLockingFailureException.class}, maxAttempts = 3, backoff = @Backoff(delay = 100))
public void updateBalance(Long userId, BigDecimal amount) {
    Wallet wallet = walletRepo.findById(userId);
    wallet.setBalance(wallet.getBalance().subtract(amount));
    walletRepo.save(wallet);
}
```

### 5.3 Atomic Database Operations (Avoid Read-Modify-Write)
- Agar possible ho, to `UPDATE wallets SET balance = balance - 2000 WHERE user_id = 123` seedha use karo. Database ke andar atomic hai, koi race condition nahi. Application ko pehle read karne ki zaroorat nahi. Balance ki current value `balance - 2000` negative ho sakti hai, to condition laga sakte ho: `WHERE user_id = 123 AND balance >= 2000`. Isse concurrency safe, lock-free, aur fast.
- **Example:** Payment deduction: `UPDATE wallets SET balance = balance - 2000 WHERE user_id = 123 AND balance >= 2000`. Agar rows affected = 1, success; else insufficient balance.

### 5.4 Conditional Update with Unique Constraint / Idempotency Key
- Agar dono services ko separate operations perform karne hain, to unhe idempotency key se link karo, aur ek hi shared row update na karein, balki alag transaction logs mein insert karein, balance ko derive karo (event sourcing).
- **Example:** Payment service insert kare `transactions(user_id, amount, type='DEBIT')`. Cashback service insert kare `transactions(user_id, amount, type='CREDIT')`. Current balance = SUM of transactions. Ye eventually consistent model hai, conflicts avoid.

### 5.5 Database Transaction Isolation Levels
- Serializable isolation level use karke conflicts detect kar sakte hain, lekin performance overhead high, aur deadlock risk. Usually optimistic locking preferred.

### 5.6 Distributed Locking (Redis / ZooKeeper)
- Agar application-level coordination chahiye across services, to distributed lock le sakte ho (e.g., Redis `SET lock:user:123 NX PX 1000`). Sirf ek service ek time pe user ka balance update kare. Lock expiration se stuck lock se bachne ke liye fencing token. (Jaise pichle sawaal mein bataya.)
- **Trade-off:** Extra latency, network calls, lock contention. Simple atomic update ke liye overkill.

### 5.7 Application-Level Serialization (Actor Model)
- Akka/Pekka actors, each entity (user) ke liye dedicated actor jo sequentially messages process kare. Concurrency handled at actor level, lost update impossible. Complex but scalable.

### 5.8 Event Sourcing & CQRS
- Commands event banake append karein (immutable). State project karein. Concurrent updates to events me resolve hote hain based on ordering, rather than lost updates.

## 6. Real Project Scenario (Detailed Example with Fix)

**Company:** Online food delivery. Order service aur payment service dono `orders` table mein status update karte hain. Order service status `CONFIRMED` karta hai, payment service status `PAID` karta hai. Parallel execution mein kabhi `PAID` status overwrite ho jaata `CONFIRMED` se, ya vice versa, order lifecycle bigad jaata.

**Root Cause:** Dono services `order_id` se row padh rahe the, status field modify kar rahe the bina version check ke. No optimistic lock.

**Fix:**
1. **Status Machine + Conditional Update:** Status transition valid state check ke saath update karo: `UPDATE orders SET status = 'PAID', version = version + 1 WHERE order_id = ? AND status = 'PENDING' AND version = ?`. Agar payment ne pehle update kar diya, to order service ka update 0 rows affect karega, wo fail ho jaayega.
2. **Optimistic Locking added:** `version` column add kiya, JPA `@Version` use kiya. Both services update with version check.
3. **Retry with Exponential Backoff:** Service failure pe message queue mein event daala, worker retry kare latest state ke saath.
4. **Idempotency:** Each update with unique `transaction_id` / idempotency key to prevent duplicate processing.

**Result:** Lost status updates eliminated, order lifecycle consistent.

## 7. Monitoring & Alerting

Concurrent update issues ko detect karna mushkil hai kyunki wo silently data corrupt karte hain. Still, kuch signals:

| Metric / Signal | How to Detect |
|----------------|---------------|
| **Optimistic lock exceptions rate** | JPA `OptimisticLockException` count spike, Spring Retry failure logs. Too many retries indicate high contention. |
| **Rows affected 0 in conditional updates** | Application log when update returns 0. Unexpected frequent 0 means conflict. |
| **Data reconciliation discrepancies** | Periodically compute checksum of critical tables against audit logs, or run sanity queries (e.g., SUM of balances). |
| **Application retry loop logs** | Warning logs "retrying due to lock failure". |
| **Database deadlock metrics** | `SHOW ENGINE INNODB STATUS` deadlocks, alert if > 0. |
| **Business metrics** | Oversold inventory, negative balance reports. |
| **Distributed lock timeout/failure** | Lock acquire failures, held duration spikes. |

**Alert:** Agar optimistic lock failure rate > 10% of updates, ya deadlocks > 5 per minute, page on-call.

## 8. Sabse Badi Seekh (Core Principle)

Concurrent updates distributed systems ki reality hai. Problem sirf tab hoti hai jab hum **read-modify-write** cycle ko atomic nahi banate. Database aur application dono ko milke ensure karna hota hai ki ek update doosre ko na khaye.

**Mantra:**
> Kabhi bhi blindly update mat karo. Hamesha ya to database atomic operations use karo (e.g., `UPDATE ... SET x = x + ?`), ya optimistic locking (version) ke saath conditional update karo, ya pessimistic locking ke saath exclusive access lo. Concurrency control sirf performance ka trade-off nahi, data correctness ka foundation hai. Har critical entity (wallet, inventory) ke liye pehle se decide karo ki conflict resolution strategy kya hogi — last write wins nahi, balki business rule based.
