## 1. Redis Crash Hone Ka Asli Matlab Kya Hai?

Redis ek in-memory data store hai jo typically **cache**, **session store**, **message queue**, ya **rate limiter** ke roop mein use hoti hai. Iski performance bahut fast hoti hai — microsecond latency — lekin ye volatile bhi hai. Agar Redis server crash ho jaaye (process mar jaaye, OOM kill, disk full, network disconnect), to application ke paas wo temporary data nahi rahega.

Application ke components jo Redis par depend karte hain, wo turant fail ho sakte hain ya unko fallback par jaana padta hai. **Database**, **backend service**, ya **user experience** par sudden load badh jaata hai. Is crash ke effect kaafi wide-ranging ho sakte hain depending on use case.

---

## 2. Real-World Example (E-commerce Product Details Cache)

Maan lo ek e-commerce site hai. Product details page baar-baar access hoti hai. Har request ke liye database se product fetch karna bahut mahnga padta hai, isliye hum Redis cache use karte hain.

Normal flow:
- User product page request → Application → Redis (key `product:123`). Agar cache hit, turant return (1 ms). Agar cache miss, DB se fetch (50 ms), Redis mein set karte hain.
- Redis mein hit ratio 95% hai, to sirf 5% requests DB pe jaati hain.

Ab **Redis crash** ho jaata hai (process SIGKILL, ya server reboot).

Result:
- Saari 100% requests DB par jaane lagti hain.
- DB suddenly 20x load face karta hai.
- Connection pool exhaust, queries queue, CPU 100%, latency spike 200ms se 10sec.
- Application threads DB response ke liye wait karte hain, thread pool bhar jaata hai.
- New requests `503 Service Unavailable` milti hain. Poori site slow ya down.

Ye exactly cache-layer failure ka cascading effect hai.

## 3. Redis Crash Kyun Hota Hai? (Root Cause Tree)

### 3.1 Out of Memory (OOM)
- `maxmemory` limit set nahi ki ya kam set ki. Redis memory exceed kar gaya, OS OOM killer ne kill kar diya.
- Data eviction policy galat set: `noeviction` se memory full par writes reject, phir bhi queries slow, eventually crash.

### 3.2 Disk I/O Issues (Persistence)
- RDB snapshot ya AOF rewrite ke waqt disk full ho jaaye, Redis I/O error se exit kar sakta hai.
- AOF file corrupt ho jaaye.

### 3.3 Configuration Errors / Bugs
- Redis version mein bug (crashes on specific commands).
- Misconfiguration: `save` directive galat, `appendfsync` settings se performance degrade, hang.

### 3.4 Network Failures
- Redis server network interface down, application se disconnect. Although Redis alive, application ke liye "crash" jaisa hi hai.

### 3.5 Power Failure / Host Crash
- Server restart, power loss. In-memory data lost (unless persistence enabled).

### 3.6 Overload / Throttling
- Too many connections, bandwidth saturate, Redis blocked commands (e.g., `KEYS *`) cause timeout, then clients assume dead.

### 3.7 Human Error
- Galati se `FLUSHALL` ya `SHUTDOWN` command de diya.
- Redis process manually kill kar diya deployment ke time.

## 4. Yeh Khatarnak Kyun Hai? (Impact on System)

### 4.1 Database Overload (Thundering Herd)
- Cache miss rates spike 100% se, DB par massive pressure. Scalability khatam.

### 4.2 Session Loss / User Logout
- Agar Redis session store hai, to saare users logged out. Login API pe sudden spike.

### 4.3 Rate Limiting Failure
- Agar Redis rate limiter ke liye use hota tha, to crash ke baad either rate limiting fail (abuse) ya aggressive fail-safe se saare requests block.

### 4.4 Message Queue / Job Data Loss
- Redis pub/sub ya list-based queues (e.g., Bull, Celery) use karte hain to pending jobs/tasks permanently lost.

### 4.5 Cache Stampede (Recovery Phase)
- Redis wapas aane ke baad jab saare clients ek saath cache populate karne lagte hain, to database phir se overload ho sakta hai. (Prateek ne iska zikr kiya.)

### 4.6 Cascading Failures in Microservices
- Multiple services same Redis cluster use karein, to ek crash se saare services degrade.

## 5. Companies Kaise Handle Karti Hain? (Prevention & Recovery Strategies)

Prateek ne high availability, replication, Sentinel, Cluster ki baat ki. Ab inhe details ke saath samjhte hain.

### 5.1 Redis Replication (Read Replicas)
- Ek primary Redis hota hai, ek ya multiple replicas. Replicas read-only hoti hain. Agar primary crash, to manual ya automatic failover se replica primary ban sakta hai.
- **Example:** Read-heavy application reads ko replicas pe redirect kar sakti hai. Agar primary crash, to ek replica ko promote karo `SLAVEOF NO ONE`. Downtime manual step se thoda hota hai.

### 5.2 Redis Sentinel (Automatic Failover)
- Sentinel ek monitoring system hai jo Redis nodes ko monitor karta hai. Agar primary down ho, to Sentinel automatic failover karta hai — replica ko primary promote karta hai, clients ko new master ka address bhejta hai.
- **Example:** Java Spring Boot Redis Sentinel configuration. Application ke `RedisConnectionFactory` Sentinel addresses ko jaanta hai. Jab primary crash, Sentinel new master elect karta hai, client transparently naye master se connect. Downtime minimal (seconds).

### 5.3 Redis Cluster (Sharding + HA)
- Data multiple shards (master nodes) mein partitioned hota hai, har master ke paas replicas hain. Agar ek master crash, to uski replica master ban jaati hai. Cluster automatic failover karta hai.
- **Example:** Twitter jaise scale par Redis Cluster use hota hai. Agar ek shard fail, bas us shard ka data temporarily unavailable (ya read-only replica se read), baaki shards normal. Full cluster crash rare.

### 5.4 Persistence (Data Recovery)
- **RDB (Snapshot):** Periodic snapshot. Crash ke baad latest snapshot se data restore. Snapshot interval ka data lost. Performance ke liye achha.
- **AOF (Append Only File):** Har write command log hota hai. Crash ke baad AOF replay se almost zero data loss. Durability ke liye `appendfsync always` ya `everysec`.
- **Hybrid:** Redis 4.0+ RDB-AOF mixed. Faster rewrites, less loss.
- **Example:** Session store ke liye AOF har second sync. Crash ke baad max 1 sec data loss. Uptime improve.

### 5.5 Client-Side Resilience (Circuit Breaker & Fallback)
- Redis client connection fail ho to application turant DB pe fallback kare? Nahi, itna sidha nahi. Instead, circuit breaker pattern use karo: agar Redis unavailable, to fast-fail karo and return stale cache (if possible) ya fallback data, na ki DB pe hammer karo.
- **Example:** Netflix Hystrix / Resilience4j circuit breaker. Redis calls fail hone par `getFallback()` mein static fallback value return karo (e.g., default product info), ya local cache (Caffeine) se serve karo.

### 5.6 Stale Cache Serving (Graceful Degradation)
- Redis unavailable ho to application local in-memory cache (e.g., Caffeine) ko use kare jo thoda outdated data store kare. Isse DB pe direct load nahi.
- **Example:** Product catalog. Local cache TTL 5 min, Redis TTL 10 min. Redis crash hone par local cache se 5 min tak serve karo, baad mein retry Redis.

### 5.7 Rate Limiting Alternative
- Agar Redis rate limiter ke liye use ho raha tha, to crash ke time fallback: either allow all requests (risk), ya block all (too safe), ya local token bucket algorithm use karo.
- **Example:** Guava RateLimiter in-memory. Distributed coordinated nahi, but temporary acceptable.

### 5.8 Monitoring & Auto-Healing
- Redis process ko systemd ya supervisor se monitor karo, crash pe auto restart.
- Kubernetes mein Redis pod liveness probe se auto restart. Agar StatefulSet with persistent volume, to data AOF se survive.

## 6. Redis Recovery Ke Baad Cache Stampede — Alag Khatarnak Scenario

Prateek ne iska zikr kiya. Redis crash ke baad jab wapas up aata hai, to cache empty hota hai. Sabhi clients ek saath database se fetch karke cache populate karna chahenge. Ye **thundering herd** database ko phir se overload kar sakta hai.

### Solution:
- **Cache warming:** Application start hone par gradually popular keys preload karo, ek sath nahi.
- **Probabilistic early expiration:** `TTL` ke saath ek random jitter daalo.
- **Request coalescing (singleflight):** Ek hi key ke liye concurrent requests ko ek hi DB call pe serialize karo. Go singleflight, Java `@Cacheable(sync=true)`.
- **Pre-computed cache:** Redis wapas aane se pehle ek separate process se data load karo.

**Example:** Spring Cache `@Cacheable` with `sync=true` ensures that only one thread fetches the data and others wait for the cache entry, avoiding stampede.

## 7. Real Project Scenario (Detailed Example with Fix)

**Company:** Online travel booking platform. Flight search results Redis mein cached hote hain (key: `flight_search:BOM-DEL:2025-12-25`). TTL 15 min. Session data bhi Redis mein (Spring Session).

**Incident:** Redis server (single instance, no replication) par disk full ho gaya. AOF rewrite fail hua, Redis ne write fail hone par process exit kar diya (persistence enabled). Redis completely down for 20 minutes.

**Immediate Impact:**
- Flight search API Redis miss hone ki vajah se sabhi requests directly database pe gayin. Database heavy join queries handle nahi kar paaya, 80% requests timeout.
- User sessions lost, all logged-in users logged out, login page pe traffic spike.
- Booking requests fail, revenue loss.

**Root Cause:** No high availability, no auto-failover, no client fallback.

**Fix Applied:**
1. **Redis Sentinel setup:** 1 master + 2 slaves, 3 sentinels. Auto failover in 10-30 sec.
2. **Persistence:** AOF everysec on all nodes.
3. **Client config:** Spring Redis `RedisConnectionFactory` using `LettuceConnectionFactory` with Sentinel configuration. Master change transparent.
4. **Cache Stampede Prevention:** Implemented `@Cacheable(sync=true)` in Spring Cache abstraction. Cache population serialized per key.
5. **Session Fallback:** Spring Session with JDBC fallback (session back in DB if Redis unavailable). Not fully, but used secondary storage.
6. **Monitoring:** Redis metrics (memory usage, connected clients, commands/sec, replication lag). `redis_master_link_down` alert if > 0 for 1 min. Ping Redis from application health check.
7. **Load testing with chaos engineering:** Random Redis kill to validate automatic failover.

**Result:** Next Redis incident resolved within 15 sec with no session loss, no cache stampede.

## 8. Monitoring & Alerting for Redis

| Metric | Description | Alert if |
|--------|-------------|----------|
| **redis_up** | Node availability | 0 for > 10 sec |
| **connected_clients** | Current client connections | Sudden drop or maxed out |
| **instantaneous_ops_per_sec** | Command rate | Drop to 0 (crash) or too high (overload) |
| **used_memory_rss** | Memory usage | Near maxmemory limit |
| **evicted_keys** | Keys evicted per sec | > 0 if policy is noeviction (memory pressure) |
| **rdb_last_save_status / aof_last_write_status** | Persistence status | "err" → disk issue |
| **rejected_connections** | Clients rejected | > 0 → limit hit |
| **master_link_down_time_seconds** | Replication lag or broken | > 30 sec |
| **keyspace_hit_ratio** | Cache hit rate | < 70% → cache ineffective, possible crash impact |
| **sentinel_known_sentinels / sentinel_known_slaves** | Sentinel status | Sentinel quorum loss |

Prometheus Redis exporter se scrape. Grafana dashboard with cluster health.

## 9. Sabse Badi Seekh (Core Principle)

Redis ek blazing-fast helper hai, **source of truth nahi hai**. Iska crash hona is baat ki yaad dilaata hai ki koi bhi cache layer fail ho sakti hai, aur application ko uske bina bhi survive karna aana chahiye. Design aise karo ki **Redis absence ho to bhi system gracefully degrade ho, na ki cascade fail**.

**Mantra:**
> Redis ko hamesha ek optional acceleration layer ki tarah treat karo. Strong consistency ke liye database, availability ke liye replication/failover, aur worst-case ke liye client-side fallback (stale cache, local cache, circuit breaker) rakho. Persistence aur auto-healing (Sentinel/Cluster) se downtime minimize karo, lekin assumption rakho ki Redis kabhi bhi gayab ho sakta hai — aur us hisaab se application resilient banao.
