## 1. Schema Migration Fail Midway Ka Asli Matlab Kya Hai?

Jaise hi tum koi database migration shuru karte ho (jaise column rename, table split, nayi table add karna), wo ek sequence of steps hota hai — SQL statements ya migration tool (Flyway, Liquibase) ke through. Agar yeh sequence beech mein kisi bhi reason se ruk jaata hai, toh database schema ek **inconsistent intermediate state** mein reh jaata hai.

Ab asli dikkat yeh hai ki tumhari application ke alag-alag instances alag-alag time pe deploy ho rahe hain (rolling deployment, canary, blue-green). Kuch instances naye code ke saath chal rahe hain jo naye schema ki expectation karte hain, aur kuch purane code ke saath jo purane schema ki.

**Partial state** ka matlab:
- Kisi table mein naya column add ho gaya, lekin sab rows ke liye default value set nahi hui.
- Foreign key constraint add ho rahi thi, lekin saari rows validate nahi hui, constraint invalid state mein hai.
- Data migration script adhi rows migrate kar ke crash ho gayi — baaki rows purane format mein hain.
- Replica databases ya read replicas sync nahi ho paaye (lag) aur unka schema purana hai.

Ye inconsistency application ke queries ko unpredictable bana deti hai — kabhi column milta hai, kabhi nahi, kabhi data format mismatch ho jata hai. Yhi **production outage** ka sabse bada karan ban sakta hai.

## 2. Real-World Example Gehraai Mein

Prateek ne `phone_number` se `mobile_number` rename ka example diya. Ise aur detail mein lete hain — imagine karo distributed e-commerce system jisme 20 microservices hain, har ek ka apna database connection aur alag deploy cycle hai.

Agar migration script ye steps karti hai:
1. `phone_number` column rename karo `mobile_number` (immediate DDL).
2. Purani records mein formatting update karo.
3. Naye column pe index banao.

Ab migration midway fail ho jaati hai step 2 pe (data migration ke time connection timeout ya deadlock). Result:
- Kuch rows mein `mobile_number` column hai, kuch rows mein abhi bhi `phone_number` hai? Nahi, rename toh step 1 mein ho gaya tha poora — sab rows mein ab column name `mobile_number` hai, lekin step 2 adhoora hai, toh kuch phone numbers `+91-...` format mein hain, kuch naye E.164 format mein convert nahi hue. Dikkat to tab aati hai jab naye code ka validation assume karta hai ki saare numbers E.164 format mein hain, aur purane code ki formatting alag hai. Par Prateek ke original example mein rename ki baat thi, to us case mein rename complete ho gaya (kyunki wo single DDL hai), par agar rename ke saath data transform bhi ho raha hai to wo incomplete reh sakta hai.

Ek aur realistic scenario: **Column type change** karna, jaise `VARCHAR(20)` se `VARCHAR(50)`, ya `INT` se `BIGINT`. Ye DDL chhoti table pe fast hai, lekin badi table pe hours le sakti hai aur lock lag sakti hai. Agar beech mein fail ho jaaye (replication lag, timeout), to database inconsistent state mein: ALTER TABLE ne poora commit nahi kiya, to rollback ho gaya? Lekin MySQL jaise kuch databases mein implicit commit hoti hai DDL ke pehle, lekin agar server crash ho jaye midway, to table corrupt bhi ho sakti hai. Ye bada khatarnaak scenario hai.

## 3. Migration Fail Midway Kyu Hoti Hai? (Root Cause Tree)

### 3.1 Infrastructure Failures
- **Network partition**: migration tool database se connection kho deta hai, adhuri migration ke saath exit kar jaata hai.
- **Deployment pipeline abort**: CI/CD agent timeout, pod eviction, etc.
- **Disk space full**: database ke paas disk nahi hai temp tables ya naye indexes ke liye.

### 3.2 Database Constraints & Locks
- **Lock timeout**: DDL statement table lock acquire nahi kar payi (koyi long-running transaction ne lock hold kiya hua tha), migration fail.
- **Deadlock**: data migration ke time concurrent writes ke saath deadlock.
- **Foreign key violation**: data migration step ne invalid data daal diya, constraint check fail.

### 3.3 Data Issues
- **Duplicate data**: unique constraint add kar rahe the, lekin already duplicates hain, migration fail.
- **Data type mismatch**: data convert karte time unexpected values (null, bad format) milti hain.
- **Large table processing timeout**: batch data migration ek connection ke andar lamba chalta hai, connection timeout ho gaya, baaki data bacha.

### 3.4 Human Error
- **Script sequence galat**: migration script mein ek step miss ho gaya, next step fail.
- **Environment mismatch**: staging pe table ka size chhota tha, production mein bahut bada; script timeout settings galat.

### 3.5 Tooling Limitations
- Flyway/Liquibase ke `flyway_schema_history` table mein entry add ho gayi lekin actual DDL fail, ab tool ko lagta hai migration successful thi. (Rare, but possible with transactional DDL issues).

## 4. Yeh Distributed Systems Mein Itni Khatarnak Kyun Hai? (Inconsistency Across Deployments)

Prateek ne sahi kaha: deployments gradual hote hain. Isko hum **"Schema-Application Contract Drift"** kehte hain.

Application ke alag-alag versions (v1 aur v2) ek saath chal rahe hain. Agar tumhara migration script ek aisa change karta hai jo backward-compatible nahi hai (jaise column rename ya drop), to v1 code fail ho jaayega kyunki wo purane column ko query kar raha hai. Ab agar migration complete bhi ho jaaye, lekin v1 ke instances abhi deploy nahi hue, to wo errors denge. Agar migration midway fail hui, to kuch databases (shards, replicas) naye schema pe hain, kuch purane pe — failure aur spread ho jaata hai.

Agar tum microservices architecture mein ho, to different services different databases share kar sakti hain, ya same database ke different tables. Ek service ka schema change doosre service ko tod sakta hai agar wo us table ko access karti hai (shared database anti-pattern, but reality hai).

Monolith se bhi bura hai: background job workers, kuch pods restart hone ke baad naye code pe, kuch purane pe. Ye "split-brain" jaisa scenario hai.

## 5. Safe Schema Migration Ka Golden Rule: Expand-Contract Pattern (Backward-Compatible)

Prateek ne "backward-compatible migrations" ka zikr kiya. Ye industry mein "Expand and Contract" ya "Parallel Change" pattern ke naam se jaana jaata hai. Iska mantra hai: **Database schema change ko multiple phases mein break karo, taaki har phase mein application ke purane aur naye dono versions saath chal sakein.**

Chalo column rename (`phone_number` → `mobile_number`) ko safe tarike se karte hain, bina midway failure ke risk ke, chahe koi bhi fail ho jaaye.

### Phase 1: Expand (Add new, keep old)
- Database mein naya column add karo `mobile_number` (nullable), sath mein data sync trigger ya application-level dual-write: dono columns mein value daalo.
- Application code update karo: naya code `mobile_number` ko read aur write kare, lekin fallback ke liye `phone_number` bhi padh sakta hai. Purana code sirf `phone_number` use karta hai.
- Is state mein chahe migration aadha ho (naya column add nahi hua kisi shard pe), application dono cases handle kar leti hai.

### Phase 2: Data Migration (Backfill)
- Background job ya migration script saari rows mein `phone_number` ki value copy karo `mobile_number` mein. Ensure trigger/application naye writes ko dono jagah daal raha hai.
- Yeh step idempotent rakho, agar midway fail bhi ho to dobara run karo, kuch nahi bigdega.

### Phase 3: Contract (Code switchover)
- Ab naye application version mein `mobile_number` primary source ban jaaye, `phone_number` ignore ho. Purane instances phir bhi `phone_number` pe chalenge. Tab tak deploy purana version hat chuka hoga.
- Agar naye version ke bugs hain, to rollback purana code pe kar sakte ho — usko `phone_number` abhi bhi mil raha hai (data sync chal raha hai).

### Phase 4: Cleanup (Drop old)
- Baad mein, jab confirm ho jaaye ki sab services naye code pe hain, tab `phone_number` column drop karo.
- Ye step kabhi midway fail hota hai to? Agar drop karte waqt fail ho jaye (timeout, lock), to application unaffected kyunki wo column use hi nahi kar rahi. Phir se try karo.

**Is approach mein midway failure ka impact minimal hai — application binary compatible rehti hai har step ke liye.**

## 6. Migration Strategies Aur Tools Jo Companies Use Karte Hain

### 6.1 Online Schema Change Tools (Zero-Downtime)

Bade tables ke liye DDL (ALTER TABLE) table lock kar sakta hai aur live traffic block kar sakta hai. Isliye companies tools use karti hain jo bina lock ke migration karte hain, jaise:

- **pt-online-schema-change (Percona)** – MySQL ke liye. Ghost table banata hai, triggers ke through live data copy karta hai, aur atomic swap karta hai.
- **gh-ost (GitHub)** – Triggerless approach, binlog replicate karta hai, aur controlled switch.
- **pg_repack / pg_squeeze** – PostgreSQL ke liye table bloat aur reorg ke saath safe migration.

In tools ki madad se agar migration fail bhi ho jaaye (e.g., copy ke dauran crash), to original table untouched rehti hai. Bas ghost table drop karo aur retry.

### 6.2 Expand-Contract with Feature Flags

Migration ke har phase ko feature flag se control karo. Flag enable hote hi naye column pe write shuru, dual read logic on/off. Koi midway fail? Flag off karo, sab purani state mein.

### 6.3 Decouple Deployment from Migration

Code deploy aur database migration ko same pipeline mein na rakho. Migration ko pehle apply karo (database schema change), fir code deploy karo. Agar migration fail, to code deploy bhi nahi hota, backward-compatible schema hai to purana code khush.

### 6.4 Blue-Green Database Strategy (Limited Use)

Some cases mein poori database ki clone (blue-green) ke saath switch karte hain. Migration new (green) db pe karo, test karo, fir traffic switch. Fail ho to old blue db pe wapas. Complex data sync cost, lekin full isolation deta hai.

## 7. Rollback — Possible Hai Ya Impossible?

Prateek ne kaha ki rollback mushkil ho sakta hai agar naya data likha ja chuka hai. Isko expand karte hain:

Rollback ke do type:
1. **Schema rollback**: database schema change ko undo karo. Column rename, add, drop ko reverse karo. Ye karna technically aasan hai, lekin agar naye column mein naye writes ke saath data loss hoga agar tum column drop karoge (data delete ho jaayega). Isliye, expand-contract pattern mein hum column drop last step mein karte hain jab purana code dead ho. Tab rollback safe hota hai.
2. **Application rollback**: code ko purane version pe revert karo. Agar tumne aise schema change kiye jo purane code ke saath compatible nahi hai (e.g., column rename bina dual-write ke), to purana code fail karega. Isliye hamesha backward-compatible migration pehle karo.

**Real rollback plan:**
- Database backup/ snapshot pehle se le lo (point-in-time recovery).
- Data migration ke step idempotent rakho; rollback ke liye inverse script pehle se ready rakho.
- Migration ko `--dry-run` mode mein test karo, aur short transactions mein break karo.
- Galat data likha gaya ho to binlog/pitr se specific rows recover karo.

## 8. Performance Impact — Large Table Migrations

Prateek ne large migrations ke performance impact ka zikr kiya. Detail mein:

- **Table locks**: Direct DDL (ALTER TABLE) MySQL 5.6 ke baad mostly online hai (INPLACE algorithm), lekin phir bhi metadata lock hota hai jo parallel DML ko block kar sakta hai. `LOCK=NONE` use karo jahaan possible.
- **Replication lag**: Row-based replication mein bade DDL se lag badh sakti hai, read replicas stale ho jaate hain, application ko old data dikhta hai. Mitigation: `pt-online-schema-change` ya `gh-ost` replicas ke lag ko monitor karte hain, automatically throttle.
- **I/O Spikes**: Index creation, data copying — disk usage aur CPU spike. To off-peak hours mein karo, ya resource throttling ke saath.
- **Long-running transactions**: Backfill data migration ko chhote batches mein karo (e.g., 1000 rows at a time with sleep), connection hold kam time ke liye, long transaction se avoid.

## 9. Monitoring & Alerting During Migration

Migration ke dauran real-time monitoring jaroori hai:

- **Database Metrics**: `Innodb_row_lock_time`, `Threads_connected`, replication lag seconds, `Queries` per second.
- **Application Metrics**: Error rate (SQLException, schema mismatch), response time spike.
- **Migration Tool Metrics**: Progress %, estimated time, throttling status.
- Alert lagayein: agar lock wait time 5 sec+ ho, ya replication lag 60 sec+ ho, ya migration stuck ho 10 min se, to on-call ko page karo.

Aur haan, migration ke baad `flyway_schema_history` ya `liquibase_changelog` verify karo — check hash match, ensure saari replicas pe apply ho gaya.

## 10. Real Project Scenario (Detailed)

Maine ek baar dekha: ek fintech app mein `users` table ka primary key `INT` se `BIGINT` aur `UUID` support ke liye migrate karna tha. Direct ALTER impossible — billion rows, hours locking.

Humne kya kiya:
1. **Expand**: Naya column `new_id` (UUID) add kiya, nullable. Application code update: write dono `id` aur `new_id`, read ke liye `id` primary, lekin `new_id` se bhi query kar sakte the (index).
2. **Backfill**: Background job (chunks of 10k) ne saari rows mein `new_id` generate kiya, progress track kiya. Job idempotent thi — retry safe.
3. **Switchover**: Feature flag ne read queries ko `new_id` pe point kiya. Dual-write continue. Monitor kiya, rollback plan tha flag off karne ka.
4. **Cleanup**: Purana `id` column drop, primary key change `new_id` pe. Phir bhi drop step midway fail ho sakta tha, lekin app unaffected kyunki wo column use nahi kar rahi thi; bas metadata lock se avoid karne ke liye `gh-ost` use kiya.

Midway failure scenario: agar backfill job beech mein crash ho jaati, to naya `new_id` kuch rows mein null. Application ki `findByNewId` query un rows ko miss karti. Isliye humne query mein fallback logic rakha: agar `new_id` se row na mile, to `id` se find karo. Toh failure ka user-visible impact zero.

## 11. Sabse Badi Seekh (Core Principle)

Schema migration sirf ek DBA task nahi hai, **yeh ek distributed system state transition hai**. Jaise distributed consensus mein nodes ke beech state agree hona chahiye, waise hi tumhare application instances aur database ke beech "schema contract" agree hona chahiye. Midway failure ka matlab hai tumhara system partitioned state mein chala gaya — kuch nodes naye contract pe, kuch purane pe.

**Isliye golden rule:**
> Kabhi bhi aisi migration mat karo jo application ke kisi bhi running version ko break kare. Har migration ko expand-contract phases mein todo, dual-read/dual-write karo, aur roll-forward ko prioritise karo rollback ke upar. Migration ko assume karo ki wo fail ho sakti hai — uske liye design karo ki fail hone par bhi system consistent ya gracefully degraded rahe.

Yahi approach large-scale production systems mein confidence deti hai. Prateek ki seekh sahi thi — "small migration mistake can quickly create production-wide issues" — isliye hum engineers ko migration ko utni hi seriousness se treat karna chahiye jitna application code change ko.

## Recap: Schema Migration Midway Failure — With Real Examples

Pichle discussion mein humne safe migration ke "Expand-Contract" pattern ki baat ki thi. Ab isi ko ekdum clear karne ke liye do real-life scenarios lete hain, aur har step mein samjhte hain ki midway fail hone par kya hota aur kaise bacha ja sakta hai.

### Example 1: `status` column rename karna (`status` → `order_status`) ek Order table mein

Socho `orders` table mein ek `status` column hai (values: 'pending', 'shipped', etc.) jise hum `order_status` rename karna chahte hain. Application ke 5 microservices is column ko read/write karte hain. Direct rename karoge to midway fail hone par kuch instances `status` dhoondhenge, kuch `order_status` — queries break, orders ruk jaayenge.

#### Safe Migration with Example

| Phase | Action | Midway failure hota hai to kya hoga? | Why safe? |
|-------|--------|--------------------------------------|-----------|
| **Phase 1: Expand** | Naya column `order_status` add (nullable). Code update: dual-write shuru — dono columns mein value daalo. Read ke liye abhi `status` hi primary. | Agar naya column add karte waqt ALTER fail (e.g., lock timeout), to purana table intact hai. Application dono columns pe dependent nahi hai, sirf purana `status` use kar rahi hai. No impact. | Purana code bina kisi badlav ke kaam karta rahega. |
| **Phase 2: Backfill** | Background script `status` ki values `order_status` mein copy kare (idempotent). | Agar script crash ho jaye midway (e.g., 60% rows backfill hue, baaki nahi), to application abhi bhi `status` read kar rahi hai, `order_status` sirf write ho raha hai. Dual-read nahi chalu hua. Phir script retry, kuch nahi bigda. | Backfill idempotent; failure pe data consistent hai, application unaffected. |
| **Phase 3: Switchover** | Feature flag `use_new_column` ON karo. Ab naya code `order_status` read karta hai, lekin fallback `status` bhi padh sakta hai. Purane instances (abhi deploy nahi hue) abhi bhi `status` padhte hain. | Agar flag ON karte hi naye code ka query bug ho aur error aaye, to flag OFF kar do — purana safe path. Fallback logic ensure karta hai ki agar `order_status` null mile (backfill incomplete due to previous failure), to `status` use karo. | Application dual-safe; rolling deployment ke time purane-naye instances coexist smoothly. |
| **Phase 4: Contract** | Ab saare instances naye code pe aa gaye. Feature flag hata do, fallback code remove. | Agar fallback remove karte waqt deployment mid-way fail (kuch instances purane code pe), to purane instances abhi bhi `status` padh rahe hain, jo dual-write ki wajah se abhi bhi up-to-date hai. No errors. | Dual-write protect karta hai jab tak saare instances update nahi hote. |
| **Phase 5: Cleanup** | `status` column drop karo. | Agar drop fail (e.g., meta data lock), to application ko koi fark nahi padta kyunki wo column use hi nahi kar rahi. Retry drop. | Application independent; data loss nahi. |

Iss example se saaf hai ki midway failure ka jadoo expand-contract pattern khatam kar deta hai — koi bhi step fail, system stable.

### Example 2: Large table partition karna (`transactions` table)

Maano `transactions` table itni badi ho gayi ki queries slow hain. Aap table ko partition karna chahte hain month-wise. Direct `ALTER TABLE ... PARTITION BY RANGE` karte waqt table lock lag sakta hai, replication lag badh sakta hai, ya midway fail ho sakta hai (disk full, timeout). Ab kya karein?

#### Safe Migration Approach with `gh-ost` (GitHub's online schema migration tool)

1. **Goal**: Bina lock aur downtime ke table partition karo, aur agar fail ho bhi jaaye to zero impact.
2. **gh-ost** ek ghost table banata hai, usme naya schema (partitions ke saath), fir original table se rows copy karta hai binlog ke zariye real-time sync karta hai.
3. **Midway failure scenario**: Network partition ki wajah se gh-ost ka MySQL se connection toot gaya, copy process stuck ya crash. **Kya hoga?**
   - Original `transactions` table intact hai, poora traffic use pe chal raha hai.
   - Ghost table incomplete hai, lekin koi application use nahi kar rahi.
   - gh-ost ka fail-safe: jab restart hota hai, wo phir se copy shuru karta hai (idempotent), ya manual drop ghost table and retry.
   - **Downtime: zero**. Bas migration delay hota hai.

Is tarah tooling aur approach se midway failure ek non-event ban jaata hai.
